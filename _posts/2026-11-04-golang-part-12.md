Bài 153 viết test cho <mark>checker</mark>, <mark>report</mark>, <mark>sites</mark>; bài 158 test <mark>notify</mark> và <mark>incident</mark>; bài 160 test <mark>slugify</mark>. Toàn những package thuần, không database, không HTTP server. Phần "khó test" của Pulse, tức là handler API, store PostgreSQL và scheduler, tới giờ vẫn chỉ được kiểm bằng tay với <mark>curl</mark>. Bài này viết test cho cả ba, mỗi loại một kỹ thuật khác nhau, rồi đưa tất cả lên GitHub Actions để mỗi lần push đều tự chạy. Không cài thêm thư viện nào: <mark>testing</mark>, <mark>httptest</mark> và các interface đã viết từ bài 153 là đủ.

#### Ba tầng test của Pulse
| Tầng | Test gì | Cần gì | Tốc độ | Bắt được lỗi gì |
|---|---|---|---|---|
| Unit | <mark>slugify</mark>, <mark>Detector</mark>, <mark>Retry</mark>, <mark>Table.Write</mark> | không gì | mili giây | logic sai |
| Handler | từng route của API, từ JSON vào tới JSON ra | store **giả** trong bộ nhớ | giây | sai mã HTTP, sai validation, lộ dữ liệu người khác |
| Integration | <mark>store.Monitors</mark>, <mark>store.Users</mark> với PostgreSQL thật | database test | vài giây | SQL sai, migration thiếu cột, <mark>Scan</mark> lệch cột |

Đây là "tháp test": nhiều test rẻ ở dưới, ít test đắt ở trên. Pulse không có tầng thứ tư (mở trình duyệt thật) vì giao diện duy nhất là trang status tĩnh, một test HTTP là đủ. Nguyên tắc chọn tầng: **test ở tầng thấp nhất mà vẫn bắt được lỗi**. Logic ngưỡng 3 lần down nằm trong <mark>Detector</mark>, test unit bắt được, không cần dựng cả server. Nhưng "Bình có xem được monitor của An không" phụ thuộc handler, middleware, và cả câu SQL có <mark>AND user_id = $2</mark>, nên cần cả tầng handler lẫn integration.

#### Bước 1: Store giả cho handler
Handler nhận <mark>monitor.Store</mark> và <mark>user.Store</mark>, hai **interface**. Bài 153 đã nói lý do dùng interface là để thay thế được; hôm nay là lúc thu lợi. Ta viết hai struct giữ dữ liệu trong map, đủ phương thức để thỏa interface. Không cần thư viện mock nào (<mark>mockgen</mark>, <mark>testify/mock</mark> có tồn tại, nhưng với interface 10 phương thức viết tay vẫn ngắn hơn và dễ đọc hơn).

File <mark>internal/api/api_test.go</mark> khá dài, đây là phần đầu:
```go
// internal/api/api_test.go (một phần: store giả)
type fakeMonitors struct {
	mu     sync.Mutex
	nextID int64
	items  map[int64]monitor.Monitor
	checks map[int64][]monitor.Check
}

func newFakeMonitors() *fakeMonitors {
	return &fakeMonitors{nextID: 1, items: map[int64]monitor.Monitor{}, checks: map[int64][]monitor.Check{}}
}

func (f *fakeMonitors) Create(ctx context.Context, m *monitor.Monitor) error {
	f.mu.Lock()
	defer f.mu.Unlock()
	m.ID = f.nextID
	f.nextID++
	m.Slug = monitor.NewSlug(m.Name)
	m.CreatedAt = time.Now()
	f.items[m.ID] = *m
	return nil
}

func (f *fakeMonitors) Get(ctx context.Context, userID, id int64) (monitor.Monitor, error) {
	f.mu.Lock()
	defer f.mu.Unlock()
	m, ok := f.items[id]
	if !ok || m.UserID != userID {
		return monitor.Monitor{}, monitor.ErrNotFound
	}
	return m, nil
}
```
Và tương tự cho <mark>List</mark>, <mark>Delete</mark>, <mark>SaveCheck</mark>, <mark>ListChecks</mark>, <mark>Stats</mark>, <mark>ListIncidents</mark>, <mark>GetBySlug</mark>, <mark>DailyUptime</mark>, cùng <mark>fakeUsers</mark> với <mark>Create</mark> (trả <mark>ErrEmailTaken</mark> nếu trùng), <mark>GetByEmail</mark>, <mark>Get</mark>. Xem đầy đủ trong zip. Vài điều đáng nói:
- File tên <mark>_test.go</mark> cùng package <mark>api</mark>: test thấy được cả hàm viết thường, và chỉ được biên dịch khi chạy <mark>go test</mark>, không bao giờ vào binary.
- Fake có mutex vì <mark>httptest.Server</mark> xử lý mỗi request trong một goroutine; <mark>-race</mark> sẽ bắt ngay nếu quên. Fake mà sai concurrency thì test báo lỗi ở chỗ không có lỗi.
- Fake mô phỏng **hành vi quan trọng** của store thật, đặc biệt là <mark>Get</mark> lọc theo <mark>userID</mark>. Nếu fake bỏ qua <mark>userID</mark>, test cách ly giữa hai người dùng sẽ xanh một cách vô nghĩa. Fake đơn giản nhưng không được dối.
- Nếu <mark>monitor.Store</mark> sau này thêm phương thức mà fake chưa có, <mark>go test</mark> **không biên dịch được** với lỗi "does not implement". Khó chịu một chút nhưng là tính năng: không bao giờ có fake lỗi thời âm thầm.

#### Bước 2: Dựng server và hai hàm tiện
```go
// internal/api/api_test.go (một phần: bộ đồ nghề)
// newTestServer dựng Server với store giả, chạy trên httptest.Server.
func newTestServer(t *testing.T) *httptest.Server {
	t.Helper()
	s := New(Deps{
		Monitors: newFakeMonitors(),
		Users:    &fakeUsers{items: map[string]user.User{}},
		Checker:  checker.New(time.Second),
		Tokens:   auth.NewTokens("test-secret-test-secret-test-secret-12", time.Hour),
	})
	srv := httptest.NewServer(s.Handler())
	t.Cleanup(srv.Close)
	return srv
}

// do gửi một request JSON, trả về mã HTTP và body đã giải mã vào out (nếu khác nil).
func do(t *testing.T, method, url, token string, body any, out any) int {
	t.Helper()
	var buf bytes.Buffer
	if body != nil {
		json.NewEncoder(&buf).Encode(body)
	}
	req, _ := http.NewRequest(method, url, &buf)
	if token != "" {
		req.Header.Set("Authorization", "Bearer "+token)
	}
	resp, err := http.DefaultClient.Do(req)
	if err != nil {
		t.Fatal(err)
	}
	defer resp.Body.Close()
	if out != nil {
		json.NewDecoder(resp.Body).Decode(out)
	}
	return resp.StatusCode
}

// signup đăng ký + đăng nhập, trả về token.
func signup(t *testing.T, base, email string) string {
	t.Helper()
	creds := map[string]string{"email": email, "password": "matkhau123"}
	if code := do(t, "POST", base+"/auth/register", "", creds, nil); code != 201 {
		t.Fatalf("register: %d", code)
	}
	var res struct{ Token string }
	if code := do(t, "POST", base+"/auth/login", "", creds, &res); code != 200 {
		t.Fatalf("login: %d", code)
	}
	return res.Token
}
```
- <mark>httptest.NewServer(s.Handler())</mark> mở một server thật trên cổng ngẫu nhiên, chạy đúng mux và middleware của production. Test gửi HTTP thật qua <mark>http.DefaultClient</mark>, nên cái gì <mark>curl</mark> thấy thì test cũng thấy. Cách nhẹ hơn là <mark>httptest.NewRecorder</mark> gọi thẳng handler không qua mạng, nhưng khi đã có middleware thì server thật dễ tin hơn.
- <mark>Cache</mark> và <mark>Limiter</mark> không gán, tức nil, nhờ bài 159 nên test không cần Redis và không bị 429 khi đăng nhập nhiều lần.
- <mark>t.Cleanup</mark> đăng ký hàm chạy khi test xong, kể cả khi test fail. Gọn hơn <mark>defer</mark> vì nằm trong hàm helper, nơi <mark>defer</mark> sẽ chạy quá sớm.
- <mark>t.Helper()</mark> ở đầu hàm tiện: khi fail, Go báo dòng trong **test** gọi helper, không phải dòng <mark>t.Fatal</mark> trong helper. Không có nó, mọi lỗi đều chỉ vào cùng một dòng của <mark>do</mark>.
- <mark>var res struct{ Token string }</mark>: khai báo struct ngay tại chỗ để nhận JSON, khi chỉ cần một trường. <mark>encoding/json</mark> khớp tên trường không phân biệt hoa thường nên <mark>Token</mark> nhận được <mark>"token"</mark>.

```go
// internal/api/api_test.go (một phần: test)
func TestAuth(t *testing.T) {
	srv := newTestServer(t)

	t.Run("đăng ký sai dữ liệu", func(t *testing.T) {
		var body map[string]any
		code := do(t, "POST", srv.URL+"/auth/register", "", map[string]string{"email": "x", "password": "1"}, &body)
		if code != 422 {
			t.Fatalf("muốn 422, nhận %d", code)
		}
		fields := body["fields"].(map[string]any)
		if fields["email"] == nil || fields["password"] == nil {
			t.Errorf("phải báo lỗi cả email lẫn password: %v", fields)
		}
	})

	t.Run("email trùng", func(t *testing.T) {
		creds := map[string]string{"email": "a@b.com", "password": "matkhau123"}
		do(t, "POST", srv.URL+"/auth/register", "", creds, nil)
		if code := do(t, "POST", srv.URL+"/auth/register", "", creds, nil); code != 409 {
			t.Errorf("muốn 409, nhận %d", code)
		}
	})

	t.Run("sai mật khẩu", func(t *testing.T) {
		creds := map[string]string{"email": "a@b.com", "password": "sai-roi"}
		if code := do(t, "POST", srv.URL+"/auth/login", "", creds, nil); code != 401 {
			t.Errorf("muốn 401, nhận %d", code)
		}
	})

	t.Run("chưa đăng nhập", func(t *testing.T) {
		if code := do(t, "GET", srv.URL+"/monitors", "", nil, nil); code != 401 {
			t.Errorf("muốn 401, nhận %d", code)
		}
		if code := do(t, "GET", srv.URL+"/monitors", "token-rac", nil, nil); code != 401 {
			t.Errorf("token rác muốn 401, nhận %d", code)
		}
	})
}
```

<mark>t.Run</mark> tạo **subtest** có tên, chạy được riêng bằng <mark>go test -run 'TestAuth/email'</mark>, và khi fail báo rõ trường hợp nào. Các subtest trong <mark>TestAuth</mark> dùng chung server và cố ý phụ thuộc thứ tự (đăng ký trước, sai mật khẩu sau); với test ngắn thế này thì chấp nhận được, nhưng mỗi <mark>TestXxx</mark> cấp cao đều tạo server riêng để độc lập nhau.

<mark>TestMonitorsIsolation</mark> là test quan trọng nhất file: nó mã hóa bài 157 thành thứ máy kiểm tra được. Sau này ai sửa <mark>findMonitor</mark> mà làm mất kiểm tra chủ sở hữu, CI đỏ ngay.

Ba test còn lại trong file: <mark>TestHealthz</mark>, <mark>TestMonitorsCRUD</mark> (tạo, liệt kê, 422 khi sai, xóa rồi 404), <mark>TestCheckNow</mark> (dựng thêm một <mark>httptest.Server</mark> làm website đích, gọi <mark>POST /monitors/1/check</mark>, kiểm tra kết quả up và stats 100%), và <mark>TestStatusPage</mark> (HTML chứa tên monitor, slug lạ trả 404). Mỗi test đọc như một kịch bản <mark>curl</mark> ở các bài trước, đó là chủ đích.

#### Bước 4: Integration test với PostgreSQL thật
Store giả không bắt được lỗi SQL. Chỉ có cách chạy với database thật:
```go
// internal/store/store_test.go (một phần)
// testDB kết nối tới database test (TEST_DATABASE_URL), chạy migration và dọn sạch bảng.
// Không có biến môi trường thì bỏ qua test: máy nào cũng chạy được `go test ./...`.
func testDB(t *testing.T) *DB {
	t.Helper()
	url := os.Getenv("TEST_DATABASE_URL")
	if url == "" {
		t.Skip("đặt TEST_DATABASE_URL để chạy test với PostgreSQL thật")
	}
	ctx := context.Background()
	db, err := Connect(ctx, url)
	if err != nil {
		t.Fatal(err)
	}
	t.Cleanup(db.Close)
	if err := db.Migrate(ctx); err != nil {
		t.Fatal(err)
	}
	// Xóa sạch trước mỗi test để test không phụ thuộc nhau. CASCADE kéo theo checks, incidents.
	if _, err := db.pool.Exec(ctx, `TRUNCATE users, monitors RESTART IDENTITY CASCADE`); err != nil {
		t.Fatal(err)
	}
	return db
}
```
- **Database test riêng**, tên <mark>pulse_test</mark>, vì mỗi test <mark>TRUNCATE</mark> sạch bảng. Trỏ nhầm vào database dev là mất hết monitor đang theo dõi. Tạo bằng <mark>docker compose exec postgres createdb -U pulse pulse_test</mark>.
- <mark>t.Skip</mark> khi thiếu biến môi trường: đồng nghiệp mới clone về, chạy <mark>go test ./...</mark> vẫn xanh, chỉ có dòng "skipped". Test chỉ chạy khi cố ý bật. Đây là cách phổ biến nhất để trộn integration test vào cùng bộ test mà không làm phiền ai.
- <mark>Migrate</mark> chạy trên database test nên **migration cũng được test**: file SQL sai cú pháp, test fail trước cả khi tới câu lệnh đầu tiên.
- <mark>RESTART IDENTITY</mark> đưa <mark>BIGSERIAL</mark> về 1, để test có thể đoán id. <mark>CASCADE</mark> xóa luôn <mark>checks</mark>, <mark>incidents</mark> đang trỏ vào monitor.

Test cho scheduler cần thấy nhất:
```go
// internal/store/store_test.go (một phần)
func TestClaimDueAndChecks(t *testing.T) {
	db := testDB(t)
	ctx := context.Background()
	monitors := NewMonitors(db)
	an := newUser(t, db, "an@example.com")

	m := monitor.Monitor{UserID: an.ID, Name: "Shop", URL: "https://shop.vn", Interval: 60}
	monitors.Create(ctx, &m)

	// Vừa tạo xong là tới giờ (next_check_at = now()).
	due, err := monitors.ClaimDue(ctx, 10)
	if err != nil || len(due) != 1 {
		t.Fatalf("ClaimDue lần 1: %v, %d monitor", err, len(due))
	}
	// Lấy xong thì lịch đã dời 60 giây: gọi lại phải rỗng.
	due, _ = monitors.ClaimDue(ctx, 10)
	if len(due) != 0 {
		t.Fatalf("ClaimDue lần 2 phải rỗng, nhận %d", len(due))
	}

	now := time.Now()
	for i, st := range []checker.Status{checker.StatusUp, checker.StatusUp, checker.StatusDown, checker.StatusUp} {
		c := monitor.Check{MonitorID: m.ID, Status: st, StatusCode: 200, LatencyMS: 100, CheckedAt: now.Add(time.Duration(i) * time.Second)}
		if err := monitors.SaveCheck(ctx, &c); err != nil {
			t.Fatal(err)
		}
	}

	got, _ := monitors.Get(ctx, an.ID, m.ID)
	if got.LastStatus != "up" {
		t.Errorf("last_status = %s, muốn up", got.LastStatus)
	}

	checks, _ := monitors.ListChecks(ctx, m.ID, 2)
	if len(checks) != 2 || !checks[0].CheckedAt.After(checks[1].CheckedAt) {
		t.Errorf("ListChecks phải mới nhất trước và tôn trọng limit: %+v", checks)
	}

	st, err := monitors.Stats(ctx, m.ID, now.Add(-time.Hour))
	if err != nil || st.TotalChecks != 4 || st.UptimePercent != 75 || st.AvgLatencyMS != 100 {
		t.Errorf("Stats: %v %+v", err, st)
	}

	days, _ := monitors.DailyUptime(ctx, m.ID, 7)
	if len(days) != 7 || days[6].Total != 4 {
		t.Errorf("DailyUptime: %d ngày, hôm nay %+v", len(days), days[len(days)-1])
	}
}
```
Mỗi khẳng định ứng với một lời hứa của bài 156: <mark>ClaimDue</mark> lấy xong thì dời lịch (lần hai rỗng), <mark>SaveCheck</mark> cập nhật <mark>last_status</mark>, <mark>ListChecks</mark> mới nhất trước, <mark>Stats</mark> tính đúng 3 up trên 4 là 75%. Ba test còn lại (<mark>TestUsers</mark>, <mark>TestMonitorsCRUD</mark>, <mark>TestIncidents</mark>) theo cùng mẫu: email trùng trả <mark>ErrEmailTaken</mark>, Bình không <mark>Get</mark> được của An, mở sự cố lần hai trả <mark>opened = false</mark> nhờ unique index.

Một lưu ý: các test này **không** gọi <mark>t.Parallel()</mark>. Chúng dùng chung một database và <mark>TRUNCATE</mark> lẫn nhau, chạy song song là hỏng. Test handler ở bước 3 thì mỗi test có server và fake riêng, song song được, bạn có thể thêm <mark>t.Parallel()</mark> làm bài tập.

#### Bước 5: Test scheduler
Scheduler có vòng lặp vô hạn với ticker, trông khó test, nhưng nó nhận <mark>context</mark> và hai interface nhỏ (bài 156), nên:
```go
// internal/scheduler/scheduler_test.go
package scheduler

import (
	"context"
	"net/http"
	"net/http/httptest"
	"sync"
	"testing"
	"time"

	"github.com/thachnguyenp/pulse/internal/checker"
	"github.com/thachnguyenp/pulse/internal/monitor"
)

// fakeStore trả về danh sách monitor "tới giờ" đúng một lần, rồi rỗng.
type fakeStore struct {
	mu    sync.Mutex
	due   []monitor.Monitor
	saved []monitor.Check
}

func (f *fakeStore) ClaimDue(ctx context.Context, limit int) ([]monitor.Monitor, error) {
	f.mu.Lock()
	defer f.mu.Unlock()
	due := f.due
	f.due = nil
	return due, nil
}

func (f *fakeStore) SaveCheck(ctx context.Context, c *monitor.Check) error {
	f.mu.Lock()
	defer f.mu.Unlock()
	f.saved = append(f.saved, *c)
	return nil
}

type fakeHandler struct {
	mu    sync.Mutex
	calls int
}

func (h *fakeHandler) Handle(ctx context.Context, m monitor.Monitor, c monitor.Check) error {
	h.mu.Lock()
	defer h.mu.Unlock()
	h.calls++
	return nil
}

func TestSchedulerRun(t *testing.T) {
	target := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.Write([]byte("ok"))
	}))
	defer target.Close()

	store := &fakeStore{due: []monitor.Monitor{
		{ID: 1, Name: "A", URL: target.URL},
		{ID: 2, Name: "B", URL: target.URL},
	}}
	handler := &fakeHandler{}
	s := New(store, checker.New(time.Second), handler, 2)

	// Chạy 2.5 giây rồi hủy: đủ cho ticker 1 giây bắn ít nhất một lần.
	ctx, cancel := context.WithTimeout(context.Background(), 2500*time.Millisecond)
	defer cancel()
	if err := s.Run(ctx); err != nil {
		t.Fatal(err)
	}

	store.mu.Lock()
	defer store.mu.Unlock()
	if len(store.saved) != 2 {
		t.Fatalf("lưu %d kết quả, muốn 2", len(store.saved))
	}
	for _, c := range store.saved {
		if c.Status != checker.StatusUp {
			t.Errorf("monitor %d: %s", c.MonitorID, c.Status)
		}
	}
	if handler.calls != 2 {
		t.Errorf("handler được gọi %d lần, muốn 2", handler.calls)
	}
}
```
<mark>context.WithTimeout</mark> 2,5 giây làm <mark>Run</mark> tự kết thúc, test không bao giờ treo. Vì <mark>Run</mark> chờ <mark>wg.Wait()</mark> trước khi trả về (bài 156), khi tới dòng kiểm tra thì mọi kết quả đã lưu xong, không cần <mark>time.Sleep</mark> đoán mò. Test này tốn 2,5 giây, hơi chậm, nhưng nó chứng minh toàn bộ vòng lặp: lấy việc, chạy song song, lưu, gọi handler, dừng sạch. Nếu muốn nhanh hơn, cho <mark>Scheduler</mark> nhận chu kỳ ticker qua tham số và test với 10ms.

Vì sao <mark>api</mark> mất tới 11 giây? **bcrypt**. Mỗi <mark>HashPassword</mark> cố ý tốn khoảng một giây (bài 157), mà mỗi <mark>signup</mark> băm một lần và so sánh một lần. Đó là thiết kế đúng cho production và sai cho test. #### Bước 7: Makefile và CI
Lệnh test có biến môi trường dài, không ai nhớ. Ghi vào <mark>Makefile</mark>, nơi lưu "các lệnh của dự án":
```makefile
# Makefile
.PHONY: run fakeweb test test-db lint

run:            ## chạy server
	go run ./cmd/pulsed

fakeweb:        ## web giả để thử
	go run ./cmd/fakeweb

test:           ## test nhanh, không cần database
	go test -race ./...

test-db:        ## test cả store với PostgreSQL thật
	TEST_DATABASE_URL=postgres://pulse:pulse@localhost:5432/pulse_test?sslmode=disable go test -race -cover ./...

lint:           ## kiểm tra định dạng và lỗi tĩnh
	gofmt -l . && go vet ./...
```
Makefile bắt buộc thụt đầu dòng bằng **tab**, không phải dấu cách. <mark>.PHONY</mark> khai báo các tên này là lệnh chứ không phải file cần build. Giờ <mark>make test</mark>, <mark>make test-db</mark> là đủ.

Rồi GitHub Actions, để mỗi push và pull request đều chạy đúng bộ lệnh đó trên máy sạch:
```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16-alpine
        env:
          POSTGRES_USER: pulse
          POSTGRES_PASSWORD: pulse
          POSTGRES_DB: pulse_test
        ports: ["5432:5432"]
        options: >-
          --health-cmd "pg_isready -U pulse"
          --health-interval 5s
          --health-timeout 5s
          --health-retries 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
      - name: Kiểm tra định dạng
        run: test -z "$(gofmt -l .)" || (gofmt -l . && exit 1)
      - name: go vet
        run: go vet ./...
      - name: Test
        env:
          TEST_DATABASE_URL: postgres://pulse:pulse@localhost:5432/pulse_test?sslmode=disable
        run: go test -race -cover ./...
      - name: Build
        run: go build ./...
```
- <mark>services</mark> khởi động một container PostgreSQL bên cạnh job, và <mark>options</mark> với <mark>pg_isready</mark> làm GitHub chờ nó sẵn sàng trước khi chạy bước đầu tiên. Không có health check, test đôi khi chạy trước khi database kịp lên và fail ngẫu nhiên.
- <mark>go-version-file: go.mod</mark>: đọc phiên bản Go từ chính <mark>go.mod</mark>, nâng cấp Go chỉ sửa một chỗ.
- Bước định dạng: <mark>gofmt -l</mark> liệt kê file chưa format; có file nào thì thất bại. Cả team code cùng một kiểu mà không cần tranh luận.
- Mật khẩu <mark>pulse</mark> nằm thẳng trong file vì database này sống 2 phút trong container rồi biến mất. Bí mật thật (token Telegram chẳng hạn) để trong Settings → Secrets của repo và đọc bằng <mark>${{ secrets.TELEGRAM_BOT_TOKEN }}</mark>; Pulse không cần vì test không gửi Telegram thật (bài 158 dùng server giả).

Đẩy lên GitHub, tab Actions hiện job chạy khoảng một phút. Từ giờ pull request nào làm đỏ CI thì không merge, đó là toàn bộ ý nghĩa của bài này.

#### Mẹo và lỗi hay gặp
- Test qua ở máy mình, fail trên CI với lỗi kết nối database: thường do quên <mark>services</mark> hoặc quên <mark>TEST_DATABASE_URL</mark> trong <mark>env</mark> của bước Test.
- <mark>go test</mark> báo "ok (cached)": kết quả cũ. Sau khi sửa migration hay dữ liệu, chạy với <mark>-count=1</mark>.
- Fake "does not implement ...: missing method X": interface vừa thêm phương thức. Thêm vào fake, thường chỉ cần trả giá trị rỗng.
- Dùng <mark>t.Fatal</mark> khi không thể tiếp tục (dựng server lỗi), <mark>t.Error</mark> khi muốn chạy tiếp để thấy hết các lỗi trong một lần. <mark>t.Fatal</mark> trong goroutine khác là lỗi, chỉ gọi từ goroutine của test.
- Test chậm làm người ta lười chạy. Giữ <mark>make test</mark> dưới 30 giây; cái gì chậm cho vào <mark>test-db</mark> hoặc đằng sau <mark>testing.Short()</mark> với cờ <mark>-short</mark>.
