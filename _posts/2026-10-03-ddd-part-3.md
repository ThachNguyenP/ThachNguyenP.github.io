Bên trong một bounded context, mọi object trong domain đều thuộc một trong 2 loại: **Entity** hoặc **Value object**. Phân biệt được 2 loại này sẽ giúp code gọn và ít bug hơn rất nhiều.

#### Entity
Entity là object có **danh tính** (identity) và **vòng đời**. Hai entity khác nhau dù mọi thuộc tính giống hệt nhau.
- 2 khách hàng cùng tên "Nguyễn Văn A", cùng sinh năm 1990, vẫn là 2 người khác nhau.
- Một đơn hàng đổi trạng thái từ <mark>pending</mark> sang <mark>paid</mark> rồi <mark>shipped</mark>, nó vẫn là **chính đơn hàng đó**.

Trong Rails, model ActiveRecord là entity, danh tính chính là <mark>id</mark>. ActiveRecord cũng so sánh 2 object bằng <mark>id</mark>
```ruby
Order.find(1) == Order.find(1) # => true, dù là 2 object khác nhau trong bộ nhớ
```
Điều quan trọng với entity là: hành vi thay đổi trạng thái phải nằm **trong** entity, như method <mark>cancel!</mark> ở bài 094. Nếu entity chỉ có getter/setter còn mọi logic nằm ở service bên ngoài, đó là **anemic domain model**, lỗi rất phổ biến trong các dự án Rails.

#### Value object
Value object là object **không có danh tính**, chỉ được định nghĩa bởi giá trị của nó.
- Tờ 100.000đ của tôi và của bạn là như nhau, không ai quan tâm số seri.
- 2 địa chỉ "12 Lê Lợi, Quận 1, TP.HCM" là một.

Đặc điểm của value object:
- **Bất biến** (immutable): muốn đổi thì tạo object mới.
- **So sánh bằng giá trị**.
- **Tự validate**: đã tạo được thì chắc chắn hợp lệ.

Ruby 3.2 trở lên có sẵn <mark>Data</mark>, sinh ra để làm value object: bất biến, so sánh bằng giá trị, có sẵn <mark>to_h</mark>, pattern matching.

#### Money
Ví dụ kinh điển nhất. Rất nhiều bug đến từ việc dùng <mark>Integer</mark> hay <mark>Float</mark> để chứa tiền: cộng VND với USD, làm tròn sai, tiền âm...
```ruby
# app/domains/shared/money.rb

module Shared
  class Money < Data.define(:amount, :currency)
    include Comparable

    class CurrencyMismatch < StandardError; end

    CURRENCIES = %w[VND USD].freeze

    def initialize(amount:, currency: "VND")
      raise ArgumentError, "amount must be Integer" unless amount.is_a?(Integer)
      raise ArgumentError, "unknown currency #{currency}" unless CURRENCIES.include?(currency)

      super
    end

    def self.zero(currency = "VND") = new(amount: 0, currency:)

    def +(other)
      ensure_same_currency!(other)
      with(amount: amount + other.amount)
    end

    def -(other)
      ensure_same_currency!(other)
      with(amount: amount - other.amount)
    end

    def *(quantity) = with(amount: amount * Integer(quantity))

    # khác loại tiền thì không so sánh được: == trả về false, còn > < sẽ raise
    def <=>(other)
      return nil unless other.is_a?(Money) && currency == other.currency

      amount <=> other.amount
    end

    def to_s = "#{amount.to_fs(:delimited, delimiter: '.')} #{currency}"

    private

    def ensure_same_currency!(other)
      raise CurrencyMismatch, "#{currency} vs #{other.currency}" if currency != other.currency
    end
  end
end
```
Dùng thử
```ruby
price = Shared::Money.new(amount: 150_000)
total = price * 3 + Shared::Money.new(amount: 30_000)
total.to_s                                       # => "480.000 VND"
total == Shared::Money.new(amount: 480_000)      # => true
total + Shared::Money.new(amount: 10, currency: "USD")
# => Shared::Money::CurrencyMismatch: VND vs USD
total.instance_variable_set(:@amount, 0)
# => FrozenError
```
Để ý <mark>with</mark>: nó không sửa object hiện tại mà trả về object mới. Đây là lý do có thể yên tâm truyền <mark>Money</mark> đi khắp nơi mà không sợ ai đó sửa mất.

Lưu ý: tôi đặt <mark>Money</mark> trong <mark>shared</mark> vì nhiều context cùng dùng. Đây chính là **shared kernel** ở bài 095. Shared kernel nên giữ **thật nhỏ**, chỉ chứa những thứ rất ổn định như Money.

#### Lưu value object vào database
Rails có sẵn <mark>composed_of</mark> để map nhiều cột thành một value object
```ruby
# app/domains/ordering/order.rb

module Ordering
  class Order < ApplicationRecord
    composed_of :total,
                class_name: "Shared::Money",
                mapping: { total_amount: :amount, total_currency: :currency }
  end
end
```
```ruby
order.total = Shared::Money.new(amount: 480_000)
order.total_amount   # => 480000
order.total          # => #<data Shared::Money amount=480000, currency="VND">
```
Hai cột này trong migration cần có giá trị mặc định (bài 097 có migration đầy đủ), nếu không đọc <mark>order.total</mark> của một đơn mới sẽ raise lỗi vì <mark>amount</mark> là <mark>nil</mark>
```ruby
t.bigint :total_amount, null: false, default: 0
t.string :total_currency, null: false, default: "VND"
```
Với value object chỉ có một cột, ví dụ <mark>Email</mark>, dùng custom attribute type sẽ gọn hơn
```ruby
# app/domains/shared/email.rb

module Shared
  class Email < Data.define(:value)
    FORMAT = URI::MailTo::EMAIL_REGEXP

    def initialize(value:)
      normalized = value.to_s.strip.downcase
      raise ArgumentError, "invalid email: #{value}" unless normalized.match?(FORMAT)

      super(value: normalized)
    end

    def domain = value.split("@").last
    def to_s = value
  end
end
```
```ruby
# app/types/email_type.rb

class EmailType < ActiveModel::Type::Value
  def cast(value)
    return value if value.nil? || value.is_a?(Shared::Email)

    Shared::Email.new(value:)
  end

  def serialize(value) = value&.to_s
end

# config/initializers/types.rb

# EmailType nằm trong app/ nên phải đăng ký trong to_prepare,
# gọi trực tiếp lúc boot sẽ bị Rails báo lỗi autoload
Rails.application.config.to_prepare do
  ActiveRecord::Type.register(:email, EmailType)
end
```
```sh
bin/rails g model Customer email:string
```
```ruby
# app/models/customer.rb

class Customer < ApplicationRecord
  attribute :email, :email
end

Customer.new(email: "  Thach@Example.COM ").email.domain # => "example.com"
```
Email luôn được chuẩn hóa ở **một chỗ duy nhất**, không cần <mark>before_save { email.downcase! }</mark> rải rác khắp các model.

#### Primitive obsession
Dấu hiệu nên tạo value object: thấy một nhóm giá trị nguyên thủy luôn đi cùng nhau, hoặc cùng một đoạn validate xuất hiện nhiều nơi.

| Thay vì | Dùng |
|---|---|
| <mark>amount</mark>, <mark>currency</mark> | <mark>Money</mark> |
| <mark>street</mark>, <mark>ward</mark>, <mark>district</mark>, <mark>city</mark> | <mark>Address</mark> |
| <mark>start_at</mark>, <mark>end_at</mark> | <mark>DateRange</mark> (có <mark>overlaps?</mark>, <mark>include?</mark>) |
| <mark>String</mark> số điện thoại | <mark>PhoneNumber</mark> (chuẩn hóa +84) |
| <mark>Integer</mark> số lượng | <mark>Quantity</mark> (không âm, có giới hạn) |

Một câu hỏi hay gặp: **Address là entity hay value object?** Câu trả lời: tùy context. Trong Ordering, địa chỉ giao hàng chỉ là giá trị, khách đổi địa chỉ thì thay cái mới. Nhưng trong một context quản lý **sổ địa chỉ** của khách, mỗi địa chỉ có id, có tên gợi nhớ ("Nhà", "Công ty"), có thể sửa, thì nó là entity. Đây chính là tinh thần của bounded context.

#### Tóm tắt
- **Entity**: có danh tính, có vòng đời, chứa hành vi thay đổi trạng thái.
- **Value object**: không danh tính, bất biến, so sánh bằng giá trị, tự validate. Ruby có sẵn <mark>Data</mark>.
- Ưu tiên value object khi có thể: dễ test, không có side effect, không lo bị sửa ngầm.

Bài tiếp theo sẽ ghép entity và value object lại thành **Aggregate**, khái niệm quan trọng nhất và cũng hay bị hiểu sai nhất của tactical design.
