5 bài trước đã đi qua từng khái niệm riêng lẻ. Bài này ghép tất cả lại thành flow **thêm vào giỏ, đặt hàng, giữ hàng trong kho**, và tổng kết những gì nên (và không nên) áp dụng trong một dự án Rails thực tế.

#### Các layer
DDD thường đi kèm với kiến trúc nhiều lớp. Phụ thuộc chỉ đi **từ ngoài vào trong**: domain không biết gì về controller hay job.

| Layer | Trách nhiệm | Trong Rails |
|---|---|---|
| **Interface** | Nhận request, trả response | Controller, GraphQL resolver, gRPC handler |
| **Application** | Điều phối use case, transaction | <mark>Ordering::PlaceOrder</mark>, <mark>Ordering::AddToCart</mark> |
| **Domain** | Quy tắc nghiệp vụ | Aggregate, value object, domain service, domain event |
| **Infrastructure** | Chi tiết kỹ thuật | Repository, adapter GHN, event bus, job, mailer |

Rails không tách được hoàn toàn domain và infrastructure, vì model ActiveRecord vừa là entity vừa biết lưu vào DB. Tôi chấp nhận điều này. Cố tách ActiveRecord ra khỏi domain (viết entity thuần Ruby + mapper) là chống lại framework, rất tốn công mà lợi ích không nhiều với phần lớn dự án.

Mỗi context là một thư mục. Muốn biết Ordering làm được gì, chỉ cần mở <mark>app/domains/ordering</mark>.

#### Thêm vào giỏ
Catalog public ra một method lấy giá
```ruby
# app/domains/catalog.rb

module Catalog
  def self.table_name_prefix = "catalog_"

  class ProductNotFound < StandardError; end

  def self.price_of(sku)
    product = Product.find_by(sku:, published: true) or raise ProductNotFound, sku
    Shared::Money.new(amount: product.price_amount, currency: product.price_currency)
  end
end
```
Application service: lấy dữ liệu, gọi domain, lưu lại. Không có <mark>if/else</mark> nghiệp vụ nào ở đây
```ruby
# app/domains/ordering/add_to_cart.rb

module Ordering
  class AddToCart
    def initialize(repository: OrderRepository.new)
      @repository = repository
    end

    def call(customer_id:, sku:, quantity:)
      order = @repository.draft_of(customer_id)
      order.add_item(sku:, quantity:, unit_price: Catalog.price_of(sku))
      @repository.save!(order)
      order
    end
  end
end
```

#### Đặt hàng
```ruby
# app/domains/ordering/place_order.rb

module Ordering
  class PlaceOrder
    def initialize(repository: OrderRepository.new)
      @repository = repository
    end

    def call(customer_id:)
      Order.transaction do
        order = @repository.draft_of(customer_id)
        order.place!
        order
      end
    end
  end
end
```
Bọc trong <mark>transaction</mark> để sau này thêm bước (áp mã giảm giá, lưu địa chỉ giao hàng...) thì tất cả cùng commit hoặc cùng rollback. Event <mark>OrderPlaced</mark> chỉ được gửi đi khi transaction này commit (bài 098).

Controller chỉ còn nhiệm vụ dịch HTTP sang use case và ngược lại
```ruby
# app/controllers/orders_controller.rb

class OrdersController < ApplicationController
  def create
    order = Ordering::PlaceOrder.new.call(customer_id: current_customer.id)
    render json: { id: order.id, status: order.status, total: order.total.to_s }, status: :created
  rescue Ordering::Order::InvalidOperation => e
    render json: { error: e.message }, status: :unprocessable_entity
  rescue ActiveRecord::StaleObjectError
    render json: { error: "Đơn hàng vừa được thay đổi, vui lòng thử lại" }, status: :conflict
  end
end
```
Lợi ích: cùng use case <mark>PlaceOrder</mark> có thể gọi từ REST, GraphQL (bài 061 - 064), gRPC (bài 065 - 068), rake task hay console mà không phải copy logic.

#### Toàn bộ flow
1. <mark>POST /orders</mark> → <mark>PlaceOrder</mark> → <mark>order.place!</mark> kiểm tra invariant, đổi trạng thái, ghi nhận <mark>OrderPlaced</mark>.
2. Transaction commit → <mark>EventBus</mark> gửi <mark>OrderPlaced</mark> → đẩy job giữ hàng, job gửi email, job cộng điểm.
3. <mark>Inventory::ReserveForOrderJob</mark> trừ kho bằng atomic update (bài 081).
4. Hết hàng → <mark>StockReservationFailed</mark> → <mark>Ordering::CancelOrderJob</mark> → <mark>order.cancel!</mark>.

Mỗi bước chỉ biết đúng phần việc của mình. Muốn thêm "gửi thông báo Slack khi có đơn trên 10 triệu"? Thêm một subscriber, không đụng vào Order.

#### Test
Đây là phần tôi thấy DDD mang lại lợi ích rõ ràng nhất. Value object và domain service test không cần database
```ruby
# test/domains/promotion/discount_calculator_test.rb

class Promotion::DiscountCalculatorTest < ActiveSupport::TestCase
  def money(amount) = Shared::Money.new(amount:)

  test "giảm theo phần trăm nhưng không vượt mức tối đa" do
    coupon = Promotion::Coupon.new(percent: 50, max_discount: money(100_000),
                                   min_subtotal: money(0), expires_at: 1.day.from_now)

    discount = Promotion::DiscountCalculator.call(coupon:, subtotal: money(1_000_000), first_order: false)

    assert_equal money(100_000), discount
  end
end
```
Aggregate test bằng cách gọi method nghiệp vụ, đọc lên giống như spec của BA
```ruby
# test/domains/ordering/order_test.rb

class Ordering::OrderTest < ActiveSupport::TestCase
  setup { @order = Ordering::Order.new(customer_id: 1) }

  test "không thể sửa đơn đã đặt" do
    @order.add_item(sku: "IP17", unit_price: Shared::Money.new(amount: 25_000_000))
    @order.place!

    assert_raises(Ordering::Order::InvalidOperation) do
      @order.add_item(sku: "CASE", unit_price: Shared::Money.new(amount: 200_000))
    end
  end

  test "không thể đặt đơn trống" do
    assert_raises(Ordering::Order::InvalidOperation) { @order.place! }
  end

  test "phát OrderPlaced khi đặt hàng" do
    published = []
    Shared::EventBus.subscribe(Ordering::OrderPlaced) { |event| published << event }

    @order.add_item(sku: "IP17", unit_price: Shared::Money.new(amount: 25_000_000))
    @order.place!

    assert_equal [@order.id], published.map(&:order_id)
  end
end
```
Để ý test cuối: từ Rails 5, <mark>after_commit</mark> vẫn chạy bình thường trong transactional test, nên có thể kiểm tra event được gửi đi bằng cách đăng ký một subscriber ngay trong test.

#### Những lỗi hay gặp
- **Anemic domain model**: model chỉ có field, logic nằm hết ở <mark>app/services</mark>. Đã làm DDD thì hành vi phải nằm trong entity/aggregate.
- **Aggregate quá to**: gom mọi thứ vào một chỗ, load chậm, lock tranh chấp. Giữ nhỏ, dùng event.
- **Copy cấu trúc mà bỏ qua ngôn ngữ**: tạo đủ folder <mark>repositories</mark>, <mark>value_objects</mark> nhưng code vẫn đặt tên <mark>status: 4</mark>. Phần quan trọng nhất của DDD là nói chuyện với domain expert.
- **Dùng chung model giữa các context**: Ordering <mark>belongs_to :product</mark> rồi gọi thẳng <mark>product.stock</mark>. Ranh giới biến mất.
- **Nghĩ DDD = microservice**: bounded context là ranh giới **logic**. Bắt đầu với modular monolith, khi nào thật sự cần thì tách context ra thành service. Lúc đó, nhờ đã có API public và event, việc tách sẽ nhẹ nhàng hơn rất nhiều.
- **Áp dụng cho mọi thứ**: trang admin, CRUD đơn giản không cần aggregate hay event. Dùng DDD cho core domain thôi.

#### Tổng kết series
| Bài | Khái niệm | Một câu |
|---|---|---|
| 094 | Ubiquitous language, Subdomain | Code nói cùng ngôn ngữ với nghiệp vụ, đầu tư vào core domain |
| 095 | Bounded context, Context map | Mỗi context một model, gọi nhau qua API public |
| 096 | Entity, Value object | Có danh tính hay chỉ là giá trị, ưu tiên value object |
| 097 | Aggregate, Repository | Ranh giới nhất quán, mọi thay đổi đi qua root |
| 098 | Domain service, Domain event | Logic giữa nhiều aggregate, thông báo những gì đã xảy ra |
| 099 | Ghép lại trong Rails | Layer, use case, test |

Nếu chỉ chọn được 2 thứ để áp dụng ngay từ ngày mai, tôi sẽ chọn **ubiquitous language** và **bounded context**. Phần tactical có thể thêm dần khi cần.
