Dự án Rails nào chạy đủ lâu cũng sẽ có một file <mark>app/models/order.rb</mark> dài cả nghìn dòng, chục cái callback gọi chéo nhau, và không ai dám sửa. Hỏi team kinh doanh "đơn hàng bị hủy thì sao?" họ trả lời một kiểu, đọc code thì thấy chạy một kiểu khác. **Domain-Driven Design** (DDD) sinh ra để giải quyết đúng vấn đề này: làm cho code phản ánh nghiệp vụ, và giữ cho nó không bị rối khi hệ thống lớn dần.

Version sử dụng: Ruby 3.4, Rails 8. Ví dụ xuyên suốt series là một shop bán hàng online, giống series Overselling (bài 081 - 084).

#### DDD là gì
DDD là cách tiếp cận được Eric Evans giới thiệu trong cuốn sách cùng tên năm 2003. Ý tưởng chính rất đơn giản:
- Phần quan trọng nhất của phần mềm là **domain**, tức là nghiệp vụ mà nó giải quyết (bán hàng, giao hàng, kế toán...), không phải framework hay database.
- Developer phải làm việc sát với **domain expert** (người hiểu nghiệp vụ: PO, BA, chính chủ shop) để cùng xây dựng một **model**, và code phải thể hiện đúng model đó.

DDD chia làm 2 phần:

| Phần | Trả lời câu hỏi | Gồm |
|---|---|---|
| **Strategic design** | Chia hệ thống thành những phần nào? | Ubiquitous language, Subdomain, Bounded context, Context map |
| **Tactical design** | Bên trong mỗi phần, code thế nào? | Entity, Value object, Aggregate, Repository, Domain service, Domain event |

Nhiều người mới học DDD thường nhảy ngay vào phần tactical (tạo folder <mark>repositories</mark>, <mark>value_objects</mark>...), nhưng theo kinh nghiệm của tôi phần strategic mới là thứ mang lại nhiều giá trị nhất.

#### Ubiquitous language
"Ngôn ngữ chung": developer, domain expert, tài liệu, và **code** đều dùng cùng một bộ từ ngữ, với cùng một ý nghĩa.

Thử đọc đoạn code này
```ruby
# app/controllers/orders_controller.rb

def update
  order = Order.find(params[:id])
  order.update!(status: 4, flag_refund: true, cancelled_by: current_user.id)
  order.items.each { |i| i.product.increment!(:qty, i.qty) }
  UserMailer.notify(order.user, "order_status_4").deliver_later
end
```
Status 4 là gì? <mark>flag_refund</mark> nghĩa là đã hoàn tiền hay cần hoàn tiền? Phải đi hỏi người viết, mà người viết đã nghỉ việc. Trong khi đó, team kinh doanh nói rất rõ: *"Khách **hủy đơn** thì **trả hàng về kho** và **hoàn tiền** nếu đã thanh toán"*. Viết lại code bằng đúng những từ đó
```ruby
# app/controllers/orders_controller.rb

def cancel
  order = Order.find(params[:id])
  order.cancel!(by: current_user, reason: params[:reason])
end
```
```ruby
# app/models/order.rb

class Order < ApplicationRecord
  enum :status, { pending: "pending", paid: "paid", shipped: "shipped", cancelled: "cancelled" }

  class CannotCancel < StandardError; end

  def cancel!(by:, reason:)
    raise CannotCancel, "Đơn đã giao cho đơn vị vận chuyển" if shipped? || cancelled?

    transaction do
      require_refund! if paid?
      restock_items!
      update!(status: :cancelled, cancelled_by: by, cancel_reason: reason)
    end
  end
end
```
Domain expert đọc tên method cũng hiểu code làm gì. Đó là mục tiêu của ubiquitous language.

Vài nguyên tắc tôi hay áp dụng:
- Làm một **bảng thuật ngữ** (glossary) ngay từ đầu, để chung trong wiki/README của dự án.
- Tên class, method, event, cột database đều lấy từ glossary. Nghiệp vụ nói "hủy đơn" thì method là <mark>cancel!</mark>, không phải <mark>update_status</mark>.
- Khi thấy domain expert dùng từ khác với code, **sửa code** (hoặc thảo luận lại), đừng để tồn tại 2 cách gọi.

| Thuật ngữ | Tiếng Anh trong code | Ý nghĩa |
|---|---|---|
| Đơn hàng | <mark>Order</mark> | Yêu cầu mua của khách, gồm nhiều dòng sản phẩm |
| Đặt hàng | <mark>place</mark> | Khách xác nhận giỏ hàng thành đơn |
| Giữ hàng | <mark>reserve</mark> | Tạm trừ tồn kho trong lúc chờ thanh toán (bài 083) |
| Hủy đơn | <mark>cancel</mark> | Chỉ được hủy khi chưa giao cho vận chuyển |
| Hoàn tiền | <mark>refund</mark> | Trả lại tiền cho đơn đã thanh toán |

#### Subdomain
Một doanh nghiệp có nhiều mảng nghiệp vụ khác nhau, gọi là **subdomain**. Với shop online:

| Subdomain | Loại | Ghi chú |
|---|---|---|
| Đặt hàng (Ordering), Khuyến mãi (Promotion) | **Core** | Thứ làm shop khác biệt với đối thủ, đáng đầu tư nhất |
| Kho (Inventory), Giao hàng (Shipping) | **Supporting** | Cần thiết, có đặc thù riêng nhưng không phải lợi thế cạnh tranh |
| Thanh toán, Gửi email, Đăng nhập | **Generic** | Ai cũng giống ai, nên dùng dịch vụ/gem có sẵn (Stripe, Devise...) |

Phân loại này giúp quyết định **đầu tư công sức vào đâu**. Áp dụng DDD đầy đủ cho phần core; phần generic thì dùng gem, đừng tự viết.

#### Khi nào không nên dùng DDD
DDD không miễn phí: nhiều class hơn, nhiều thảo luận hơn. Nó **không đáng** khi:
- Ứng dụng chủ yếu là CRUD: admin page, form nhập liệu, blog... Rails scaffold là đủ.
- Nghiệp vụ đơn giản, ít thay đổi.
- Không có ai hiểu nghiệp vụ để cùng làm model.

Ngược lại, khi nghiệp vụ phức tạp, nhiều quy tắc, thay đổi liên tục, nhiều team cùng làm, thì DDD rất đáng để thử. Và tin vui là không cần áp dụng tất cả: chỉ riêng ubiquitous language và bounded context đã cải thiện code rất nhiều.
