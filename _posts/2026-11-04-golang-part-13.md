Pulse đã có đủ tính năng và có test. Nhưng khi nó chạy trên server, lúc 2 giờ sáng, khách nhắn "API chậm quá" hoặc "tôi bấm đăng nhập bị lỗi", bạn trả lời bằng gì? Bài này gắn cho pulsed ba thứ để **nhìn thấy nó đang làm gì từ bên ngoài**: log có cấu trúc (JSON) kèm request id, metrics cho Prometheus, và pprof để soi bên trong tiến trình Go khi nó ăn CPU hay rò rỉ goroutine. Bài 071 - 074 đã nói về observability trong Rails; hôm nay làm lại bằng Go, và sẽ thấy phần lớn là thư viện chuẩn.

#### Ba trụ của observability
| Trụ | Trả lời câu hỏi | Pulse dùng |
|---|---|---|
| **Logs** | Chuyện gì đã xảy ra với *request này*? | <mark>log/slog</mark> (thư viện chuẩn), JSON trên production |
| **Metrics** | Hệ thống *nói chung* đang thế nào? Bao nhiêu request/giây, p95 bao nhiêu ms, bao nhiêu monitor down? | Prometheus client + endpoint <mark>/metrics</mark> |
| **Traces** | Một request đi qua những service nào, mỗi chặng mất bao lâu? | Chưa làm; bước tiếp theo là OpenTelemetry (bài 074 có bản Rails) |

Log là chi tiết nhưng đắt (mỗi request một dòng, tìm kiếm chậm). Metrics là rẻ (vài con số cộng dồn trong bộ nhớ) nhưng không nói được về *một* request cụ thể. Dùng cả hai: metrics báo "p95 tăng gấp đôi từ 14:00", log cho biết tại sao.

#### Bước 1: Log có cấu trúc với slog
Từ bài 5 ta đã gọi <mark>slog.Info("request", "method", r.Method, ...)</mark>. Đó là **structured logging**: thay vì ghép chuỗi <mark>"GET /monitors 200 3ms"</mark>, ta ghi từng cặp key-value. Máy đọc được, nên tìm "mọi request có <mark>status=500</mark> trong 10 phút qua" là một câu lọc, không phải regex.

Tới giờ slog in dạng text (logger mặc định). Production cần **JSON**: Loki, Datadog, CloudWatch, Elasticsearch đều ăn JSON thẳng, mỗi key thành một trường để lọc. Thêm ba biến cấu hình:
```go
// internal/config/config.go (thêm vào Config và Load)
	DebugAddr    string // pprof, để trống thì tắt
	LogFormat    string // "text" khi dev, "json" trên production
	LogLevel     string // debug, info, warn, error
	...
		DebugAddr:    os.Getenv("DEBUG_ADDR"),
		LogFormat:    getenv("LOG_FORMAT", "text"),
		LogLevel:     getenv("LOG_LEVEL", "info"),
```
Và một hàm dựng logger trong <mark>cmd/pulsed/main.go</mark>, gọi ngay sau <mark>config.Load()</mark>:
```go
// cmd/pulsed/main.go (thêm)
// setupLogger chọn định dạng log: text dễ đọc khi dev, JSON cho máy đọc trên production.
func setupLogger(cfg config.Config) {
	var level slog.Level
	if err := level.UnmarshalText([]byte(strings.ToUpper(cfg.LogLevel))); err != nil {
		level = slog.LevelInfo
	}
	opts := &slog.HandlerOptions{Level: level}

	var handler slog.Handler = slog.NewTextHandler(os.Stdout, opts)
	if cfg.LogFormat == "json" {
		handler = slog.NewJSONHandler(os.Stdout, opts)
	}
	slog.SetDefault(slog.New(handler))
}
```
Vài điểm mới:
- <mark>slog.Level</mark> có phương thức <mark>UnmarshalText</mark>: đưa chuỗi <mark>"DEBUG"</mark>, <mark>"WARN"</mark> vào là ra mức tương ứng, sai thì báo lỗi và ta rơi về Info. Đây là cách chuẩn để đọc enum từ chuỗi trong Go, nhiều kiểu trong thư viện chuẩn có nó.
- <mark>slog.Handler</mark> là interface, hai hiện thực sẵn: <mark>TextHandler</mark> và <mark>JSONHandler</mark>. Ta khai báo biến kiểu interface rồi gán hiện thực tùy cấu hình, đúng cách làm ở bài 4.
- <mark>slog.SetDefault</mark> thay logger toàn cục. Mọi chỗ đã gọi <mark>slog.Info</mark> trong api, scheduler, notify **không phải sửa gì**. Đó là lý do ngay từ bài 5 ta dùng slog chứ không dùng <mark>fmt.Println</mark>.
- Log ghi ra **stdout**, không ghi file. Trên server, Docker hay systemd gom stdout lại; app không cần biết log đi đâu.

Mức log dùng thế nào: <mark>Debug</mark> cho thứ chỉ bạn cần khi đang sửa lỗi (tắt trên production), <mark>Info</mark> cho sự kiện bình thường (request, đã kiểm tra monitor), <mark>Warn</mark> cho chuyện bất thường nhưng tự xử lý được (gửi Telegram lỗi, thử lại), <mark>Error</mark> cho chuyện cần người xem (không lưu được database).

Chạy với <mark>LOG_FORMAT=json go run ./cmd/pulsed</mark>:
```
{"time":"2026-11-04T23:39:00.17585+07:00","level":"INFO","msg":"database sẵn sàng"}
{"time":"2026-11-04T23:39:00.184167+07:00","level":"INFO","msg":"redis sẵn sàng"}
{"time":"2026-11-04T23:39:00.184188+07:00","level":"WARN","msg":"chưa cấu hình TELEGRAM_BOT_TOKEN/TELEGRAM_CHAT_ID hay WEBHOOK_URL, thông báo chỉ ghi log"}
```
Khó đọc hơn cho mắt người, nhưng đó là định dạng dành cho máy.

#### Bước 2: Request ID
Khách báo "tôi bấm tạo monitor bị lỗi lúc 14:32". Server lúc đó xử lý vài trăm request. Dòng log nào là của khách? Cách giải quyết chuẩn: gắn cho mỗi request một **id ngẫu nhiên**, trả về trong header <mark>X-Request-ID</mark>, và ghi id đó vào mọi dòng log của request. Khách (hoặc frontend) gửi id lên khi báo lỗi, bạn grep đúng một id.

Viết lại <mark>internal/api/middleware.go</mark>, giờ có ba middleware và thêm metrics (bước 3):
```go
// internal/api/middleware.go
package api

import (
	"context"
	"crypto/rand"
	"encoding/hex"
	"log/slog"
	"net/http"
	"strconv"
	"time"

	"github.com/thachnguyenp/pulse/internal/metrics"
)

// statusRecorder nhớ lại mã HTTP mà handler đã ghi, để log được.
type statusRecorder struct {
	http.ResponseWriter
	status int
}

func (r *statusRecorder) WriteHeader(code int) {
	r.status = code
	r.ResponseWriter.WriteHeader(code)
}

type requestIDKey struct{}

// RequestID lấy id của request từ context, để handler ghi log kèm id.
func RequestID(ctx context.Context) string {
	id, _ := ctx.Value(requestIDKey{}).(string)
	return id
}

// requestID gắn cho mỗi request một id ngẫu nhiên, trả về trong header
// để khi khách báo lỗi, ta tìm đúng dòng log.
func requestID(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		id := r.Header.Get("X-Request-ID")
		if id == "" {
			b := make([]byte, 8)
			rand.Read(b)
			id = hex.EncodeToString(b)
		}
		w.Header().Set("X-Request-ID", id)
		next.ServeHTTP(w, r.WithContext(context.WithValue(r.Context(), requestIDKey{}, id)))
	})
}

// logging ghi một dòng log và cập nhật metrics cho mỗi request.
func logging(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		rec := &statusRecorder{ResponseWriter: w, status: http.StatusOK}

		next.ServeHTTP(rec, r)

		elapsed := time.Since(start)
		// r.Pattern là mẫu route đã khớp ("GET /monitors/{id}"), không phải path thật,
		// nên số nhãn metric không phình theo số id.
		route := r.Pattern
		if route == "" {
			route = "unmatched"
		}
		metrics.HTTPRequests.WithLabelValues(route, strconv.Itoa(rec.status)).Inc()
		metrics.HTTPDuration.WithLabelValues(route).Observe(elapsed.Seconds())

		slog.Info("request",
			"request_id", RequestID(r.Context()),
			"method", r.Method,
			"path", r.URL.Path,
			"status", rec.status,
			"duration_ms", float64(elapsed.Microseconds())/1000,
		)
	})
}

// recoverPanic bắt panic trong handler, trả 500 thay vì làm sập cả server.
func recoverPanic(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		defer func() {
			if err := recover(); err != nil {
				slog.Error("panic", "request_id", RequestID(r.Context()), "error", err, "path", r.URL.Path)
				writeError(w, http.StatusInternalServerError, "lỗi hệ thống")
			}
		}()
		next.ServeHTTP(w, r)
	})
}
```
Những gì đáng chú ý:
- <mark>crypto/rand</mark> chứ không phải <mark>math/rand</mark>: 8 byte ngẫu nhiên thật, mã hex thành 16 ký tự. Đủ ngắn để khách đọc qua điện thoại, đủ dài để không trùng.
- Nếu client đã gửi <mark>X-Request-ID</mark> (frontend, API gateway, hay một service khác gọi sang) thì **giữ nguyên**, để một id theo xuyên suốt nhiều service. Đây chính là ý tưởng sơ khai của tracing.
- Id được cất vào context với key là kiểu riêng <mark>requestIDKey{}</mark>, giống cách cất user id ở bài 8. Hàm <mark>RequestID(ctx)</mark> xuất ra ngoài để handler nào cũng lấy được.
- <mark>duration_ms</mark> là số thực thay vì chuỗi <mark>"3.2ms"</mark> như trước. Lý do: khi log là JSON, số mới lọc được kiểu <mark>duration_ms > 500</mark>; chuỗi thì không.

Ghép vào <mark>Handler()</mark>, thứ tự quan trọng:
```go
// internal/api/server.go (sửa dòng return)
	return requestID(recoverPanic(logging(mux)))
```
Request đi từ ngoài vào: <mark>requestID</mark> trước (để mọi lớp sau đều có id), rồi <mark>recoverPanic</mark> (bọc ngoài <mark>logging</mark> để nếu chính logging panic cũng bắt được), rồi <mark>logging</mark>, rồi mux. Thử:
```sh
curl -s -i localhost:3000/healthz | grep -i x-request-id
# X-Request-Id: a849b817fec364b4
```
Và dòng log tương ứng có <mark>request_id=a849b817fec364b4</mark>. Hãy đưa id này vào thông báo lỗi 500 trả cho client nữa (bài tập cuối bài).

#### Bước 3: Metrics với Prometheus
Prometheus là hệ thống metrics phổ biến nhất trong thế giới Go và Kubernetes. Mô hình của nó là **pull**: app không gửi gì đi cả, chỉ mở một endpoint <mark>/metrics</mark> trả về các con số dạng text; Prometheus cứ 15 giây gọi vào lấy một lần và lưu thành chuỗi thời gian. App chết thì Prometheus biết ngay vì gọi không được.

Cài thư viện chính thức:
```sh
go get github.com/prometheus/client_golang
```
Khai báo các số đo trong một package riêng, để api, scheduler, incident cùng dùng mà không import lẫn nhau:
```go
// internal/metrics/metrics.go
// Package metrics khai báo các số đo Prometheus của pulsed.
package metrics

import (
	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/promauto"
)

// promauto tự đăng ký với registry mặc định; /metrics đọc từ đó.
var (
	HTTPRequests = promauto.NewCounterVec(prometheus.CounterOpts{
		Name: "pulse_http_requests_total",
		Help: "Số request HTTP, theo route và mã trả về.",
	}, []string{"route", "status"})

	HTTPDuration = promauto.NewHistogramVec(prometheus.HistogramOpts{
		Name:    "pulse_http_request_duration_seconds",
		Help:    "Thời gian xử lý request HTTP.",
		Buckets: []float64{.005, .01, .025, .05, .1, .25, .5, 1, 2.5},
	}, []string{"route"})

	Checks = promauto.NewCounterVec(prometheus.CounterOpts{
		Name: "pulse_checks_total",
		Help: "Số lần kiểm tra monitor, theo kết quả.",
	}, []string{"status"})

	CheckLatency = promauto.NewHistogram(prometheus.HistogramOpts{
		Name:    "pulse_check_latency_seconds",
		Help:    "Thời gian website được theo dõi phản hồi.",
		Buckets: []float64{.05, .1, .25, .5, 1, 2.5, 5, 10},
	})

	Notifications = promauto.NewCounterVec(prometheus.CounterOpts{
		Name: "pulse_notifications_total",
		Help: "Số thông báo đã gửi, theo kết quả.",
	}, []string{"result"})
)
```
Hai loại số đo dùng ở đây:
- **Counter**: chỉ tăng, không bao giờ giảm. "Tổng số request từ lúc khởi động". Tự nó vô nghĩa (reset khi restart), nhưng Prometheus tính được *tốc độ* từ nó: <mark>rate(...[5m])</mark> là số request mỗi giây trong 5 phút qua.
- **Histogram**: đếm số quan sát rơi vào từng **bucket** (≤ 5ms, ≤ 10ms, ≤ 25ms...). Từ đó tính được p50, p95, p99. Bucket phải chọn theo thứ đo: request API thường vài ms tới vài trăm ms, nên bucket từ 5ms tới 2.5s; còn website được theo dõi phản hồi chậm hơn nhiều, bucket từ 50ms tới 10s (bằng timeout của checker). Chọn sai bucket thì p95 ra con số vô nghĩa vì mọi thứ dồn vào một ô.

Phần <mark>[]string{"route", "status"}</mark> là **label**: mỗi tổ hợp giá trị label là một chuỗi thời gian riêng. Đây là chỗ người mới hay làm sập Prometheus: nếu label là <mark>path</mark> thật thì <mark>/monitors/1</mark>, <mark>/monitors/2</mark>... mỗi id một chuỗi, hàng triệu chuỗi, gọi là **cardinality explosion**. Vì vậy middleware dùng <mark>r.Pattern</mark>, trường có từ Go 1.22 cho biết **mẫu route đã khớp** (<mark>GET /monitors/{id}</mark>), chỉ vài chục giá trị. Quy tắc: không bao giờ đặt user id, email, request id, URL đầy đủ làm label. Những thứ đó thuộc về log.

Gắn vào hai chỗ còn lại. Scheduler đếm kết quả và độ trễ của website được theo dõi:
```go
// internal/scheduler/scheduler.go (thêm vào runOne, ngay sau CheckFromResult)
	metrics.Checks.WithLabelValues(string(c.Status)).Inc()
	metrics.CheckLatency.Observe(float64(c.LatencyMS) / 1000)
```
Detector đếm thông báo gửi được hay không:
```go
// internal/incident/detector.go (sửa hàm notify)
func (d *Detector) notify(ctx context.Context, e notify.Event) error {
	if err := d.notifier.Notify(ctx, e); err != nil {
		metrics.Notifications.WithLabelValues("error").Inc()
		return fmt.Errorf("gửi thông báo: %w", err)
	}
	metrics.Notifications.WithLabelValues("ok").Inc()
	return nil
}
```
(Nhớ thêm <mark>"github.com/thachnguyenp/pulse/internal/metrics"</mark> vào import của hai file.) Prometheus quy ước tên metric: tiền tố là tên app, đơn vị nằm trong tên (<mark>_seconds</mark>, <mark>_bytes</mark>), counter kết thúc bằng <mark>_total</mark>. Độ trễ đo bằng **giây** dù ta lưu mili giây trong database, vì cả hệ sinh thái Prometheus dùng giây.

Mở endpoint:
```go
// internal/api/server.go (thêm sau route /healthz)
	mux.Handle("GET /metrics", promhttp.Handler())
```
với import <mark>"github.com/prometheus/client_golang/prometheus/promhttp"</mark>. Chạy server, gọi vài request, chờ scheduler kiểm tra vài monitor rồi xem:
```sh
curl -s localhost:3000/metrics | grep ^pulse_
```
```
pulse_check_latency_seconds_count 5
pulse_checks_total{status="down"} 1
pulse_checks_total{status="up"} 4
pulse_http_request_duration_seconds_count{route="GET /healthz"} 1
pulse_http_request_duration_seconds_count{route="GET /monitors"} 1
pulse_http_requests_total{route="GET /healthz",status="200"} 1
pulse_http_requests_total{route="GET /monitors",status="401"} 1
```
Đó là định dạng text của Prometheus. Ngoài <mark>pulse_*</mark>, thư viện còn tự thêm <mark>go_goroutines</mark>, <mark>go_memstats_*</mark>, <mark>process_cpu_seconds_total</mark>: số goroutine, bộ nhớ, CPU của tiến trình, miễn phí.

#### Bước 4: Chạy Prometheus để nhìn
Thêm Prometheus vào compose, nhưng dưới một **profile** để <mark>docker compose up</mark> bình thường không kéo nó theo:
```yaml
# docker-compose.yml (thêm service)
  # Tùy chọn: docker compose --profile monitoring up -d
  prometheus:
    image: prom/prometheus:v3.5.0
    profiles: [monitoring]
    ports:
      - "9090:9090"
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml:ro
```
```yaml
# prometheus.yml
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: pulsed
    static_configs:
      # host.docker.internal: từ trong container gọi ra máy host (Docker Desktop)
      - targets: ["host.docker.internal:3000"]
```
<mark>docker compose --profile monitoring up -d</mark>, mở <mark>http://localhost:9090</mark>, gõ vài câu PromQL:

| Câu hỏi | PromQL |
|---|---|
| Request mỗi giây, theo route | <mark>rate(pulse_http_requests_total[5m])</mark> |
| p95 thời gian xử lý | <mark>histogram_quantile(0.95, rate(pulse_http_request_duration_seconds_bucket[5m]))</mark> |
| Tỷ lệ lỗi 5xx | <mark>sum(rate(pulse_http_requests_total{status=~"5.."}[5m])) / sum(rate(pulse_http_requests_total[5m]))</mark> |
| Số lần kiểm tra down | <mark>pulse_checks_total{status="down"}</mark> |
| Goroutine đang sống | <mark>go_goroutines</mark> |

Bước tiếp theo tự nhiên là **Grafana** (bài 073 có hướng dẫn): nối vào Prometheus, vẽ dashboard từ đúng các câu trên, và đặt alert "tỷ lệ 5xx > 1% trong 5 phút thì báo". Pulse giám sát website của người khác; Prometheus + Grafana giám sát chính Pulse.

#### Bước 5: pprof, nhìn vào bên trong tiến trình
Log và metrics nói chuyện gì xảy ra. Khi câu hỏi là "sao pulsed ăn 100% CPU" hay "sao bộ nhớ tăng mãi", bạn cần nhìn vào **bên trong** tiến trình. Go có sẵn **pprof**, và bật nó chỉ cần một dòng import:
```go
// cmd/pulsed/main.go (thêm vào import)
	_ "net/http/pprof" // đăng ký /debug/pprof/* vào http.DefaultServeMux
```
Dấu gạch dưới là **blank import**: import package chỉ để chạy hàm <mark>init()</mark> của nó, không dùng tên nào cả. <mark>init()</mark> của <mark>net/http/pprof</mark> đăng ký các route <mark>/debug/pprof/*</mark> vào <mark>http.DefaultServeMux</mark>, cái mux toàn cục mà <mark>http.HandleFunc</mark> ở fakeweb (bài 3) từng dùng.

Nhưng pulsed dùng mux riêng (<mark>http.NewServeMux()</mark> ở bài 5), nên các route này **không** lộ ra cổng 3000. Đó là điều ta muốn: pprof cho phép tải profile CPU, bộ nhớ, danh sách goroutine kèm mã nguồn, không bao giờ được public. Mở nó trên một cổng riêng chỉ khi có cấu hình, trong errgroup cùng server và scheduler:
```go
// cmd/pulsed/main.go (thêm vào run, trước g.Go chờ ctx.Done)
	if cfg.DebugAddr != "" {
		// pprof trên cổng riêng, chỉ mở trong mạng nội bộ, không bao giờ public.
		g.Go(func() error {
			slog.Info("pprof đang chạy", "addr", cfg.DebugAddr)
			return http.ListenAndServe(cfg.DebugAddr, http.DefaultServeMux)
		})
	}
```
<mark>DEBUG_ADDR=127.0.0.1:6060</mark> trong <mark>.env</mark>: chỉ lắng nghe trên loopback. Trên server, muốn xem thì SSH vào và gọi local. Thử:
```sh
curl -s "localhost:6060/debug/pprof/goroutine?debug=1" | head -3
```
```
goroutine profile: total 14
```

Phân tích bằng công cụ đi kèm Go:
```sh
go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30
# (pprof) top        -> 10 hàm tốn CPU nhất
# (pprof) web        -> vẽ đồ thị (cần Graphviz)
```
Rò rỉ goroutine trong Go thường có hai dạng, cả hai ta đều đã gặp mặt trái của nó trong series:
1. Goroutine **chờ gửi vào channel** mà không ai nhận (bài 3: nếu <mark>checkAll</mark> không có <mark>close(jobs)</mark>, 10 worker đứng chờ mãi). Mỗi request tạo một goroutine như vậy thì số goroutine tăng theo số request.
2. Quên <mark>resp.Body.Close()</mark> (bài 1): kết nối HTTP không trả về pool, mỗi kết nối kèm goroutine đọc. Profile goroutine sẽ thấy hàng trăm goroutine đứng ở <mark>net/http.(*persistConn).readLoop</mark>.

Khi thấy dạng stack lặp lại hàng trăm lần trong profile, bạn đã có thủ phạm kèm số dòng. Đó là thứ không ngôn ngữ nào cho bạn dễ như Go.

#### Mẹo và lỗi hay gặp
- **Log quá nhiều**: scheduler ghi một dòng "đã kiểm tra" mỗi lần check. 1.000 monitor mỗi phút là 1,4 triệu dòng mỗi ngày. Trên production, hạ xuống <mark>Debug</mark> hoặc chỉ log khi trạng thái đổi; đã có metric <mark>pulse_checks_total</mark> đếm thay.
- **Đừng log dữ liệu nhạy cảm**: mật khẩu, token, body request. Middleware logging của ta cố tình không log body hay header <mark>Authorization</mark>.
- **Metric có label nhưng chưa có giá trị** thì không hiện trên <mark>/metrics</mark> (ví dụ chưa có check nào down thì không có dòng <mark>status="down"</mark>). Dashboard Grafana cần xử lý "không có dữ liệu" khác "bằng 0".
- **Histogram không hợp nhất được** giữa các bucket khác nhau: đổi <mark>Buckets</mark> sau khi đã chạy một thời gian là đổi ý nghĩa dữ liệu cũ. Chọn kỹ một lần.
- **pprof trên cổng public** là lỗi bảo mật kinh điển trong các dự án Go. Luôn <mark>127.0.0.1</mark> hoặc để trống <mark>DEBUG_ADDR</mark>.
