Pulse tới giờ đã chạy được việc chính: kiểm tra, lưu, báo động. Bài này giải quyết hai vấn đề sẽ gặp ngay khi có người dùng thật. Một, <mark>GET /monitors/{id}/stats</mark> chạy câu <mark>avg</mark> trên bảng <mark>checks</mark> mỗi lần gọi, trang nào hiện số uptime cũng gọi nó, mà kết quả chỉ đổi mỗi vài chục giây. Hai, <mark>POST /auth/login</mark> đang cho phép thử mật khẩu bao nhiêu lần tùy thích. Cả hai đều giải quyết bằng **Redis**, và qua đó học một thói quen Go rất hay: viết code sao cho **thiếu Redis thì chương trình vẫn chạy**.

#### Redis là gì
Redis là một database **trong bộ nhớ**, kiểu key-value: <mark>SET stats:6 "{...}"</mark>, <mark>GET stats:6</mark>. Vì nằm trong RAM nên đọc ghi mất vài chục micro giây, nhanh hơn PostgreSQL cả trăm lần cho những việc đơn giản. Ba tính năng ta dùng hôm nay:

| Lệnh | Ý nghĩa | Dùng cho |
|---|---|---|
| <mark>SET key value EX 30</mark> | lưu kèm thời hạn 30 giây, hết hạn tự xóa | cache |
| <mark>INCR key</mark> | tăng số đếm lên 1, **atomic**: hai request cùng lúc không bao giờ đếm trùng | rate limit |
| <mark>EXPIRE key 60</mark>, <mark>TTL key</mark> | đặt hạn, hỏi còn bao lâu | rate limit |

Bạn đã gặp Redis ở bài 084 (flash sale với Ruby). Ý tưởng không đổi, chỉ đổi ngôn ngữ.

Hai kiểu dùng Redis trong bài:
- **Cache-aside**: trước khi tính toán tốn kém, hỏi cache. Có thì trả luôn. Không thì tính, cất vào cache với thời hạn, rồi trả. Lần sau trong 30 giây tới ai hỏi cũng nhận bản trong cache.
- **Rate limit**: mỗi IP một bộ đếm, mỗi phút reset. Quá 10 lần thì trả 429.

#### Bước 1: Package cache
```go
// internal/cache/cache.go
// Package cache lưu tạm dữ liệu tính toán tốn kém vào Redis.
package cache

import (
	"context"
	"encoding/json"
	"errors"
	"fmt"
	"time"

	"github.com/redis/go-redis/v9"
)

// Cache bọc kết nối Redis. Mọi phương thức chấp nhận receiver nil:
// không cấu hình Redis thì cache coi như luôn "miss", chương trình vẫn chạy.
type Cache struct {
	rdb *redis.Client
}

// Connect mở kết nối tới Redis theo URL dạng redis://host:6379/0.
func Connect(ctx context.Context, url string) (*Cache, error) {
	opt, err := redis.ParseURL(url)
	if err != nil {
		return nil, fmt.Errorf("REDIS_URL không hợp lệ: %w", err)
	}
	rdb := redis.NewClient(opt)
	if err := rdb.Ping(ctx).Err(); err != nil {
		return nil, fmt.Errorf("không kết nối được Redis: %w", err)
	}
	return &Cache{rdb: rdb}, nil
}

// Client trả về kết nối Redis thô cho các package khác (rate limit).
func (c *Cache) Client() *redis.Client {
	if c == nil {
		return nil
	}
	return c.rdb
}

func (c *Cache) Close() error {
	if c == nil {
		return nil
	}
	return c.rdb.Close()
}

// Get đọc key và giải mã JSON vào v. found=false nếu không có hoặc đã hết hạn.
func (c *Cache) Get(ctx context.Context, key string, v any) (found bool, err error) {
	if c == nil {
		return false, nil
	}
	data, err := c.rdb.Get(ctx, key).Bytes()
	if errors.Is(err, redis.Nil) {
		return false, nil
	}
	if err != nil {
		return false, err
	}
	return true, json.Unmarshal(data, v)
}

// Set mã hóa v thành JSON và lưu với thời hạn ttl.
func (c *Cache) Set(ctx context.Context, key string, v any, ttl time.Duration) error {
	if c == nil {
		return nil
	}
	data, err := json.Marshal(v)
	if err != nil {
		return err
	}
	return c.rdb.Set(ctx, key, data, ttl).Err()
}

// Delete xóa các key, dùng khi dữ liệu gốc vừa đổi.
func (c *Cache) Delete(ctx context.Context, keys ...string) error {
	if c == nil || len(keys) == 0 {
		return nil
	}
	return c.rdb.Del(ctx, keys...).Err()
}
```
Vài điểm mới:
- <mark>redis.ParseURL</mark> đọc chuỗi <mark>redis://user:pass@host:6379/0</mark>, giống <mark>DATABASE_URL</mark> ở bài 155. Một biến môi trường cho mọi thông tin kết nối.
- Mọi lệnh của go-redis trả về một "cmd", gọi <mark>.Err()</mark>, <mark>.Result()</mark>, <mark>.Bytes()</mark> để lấy kết quả. Key không tồn tại thì lỗi là <mark>redis.Nil</mark>, so sánh bằng <mark>errors.Is</mark> giống <mark>pgx.ErrNoRows</mark>. "Không có" không phải lỗi thật, nên <mark>Get</mark> dịch nó thành <mark>found = false</mark>.
- Redis chỉ lưu chuỗi và byte. Struct Go muốn bỏ vào phải **mã hóa**, ta dùng JSON vì đã có sẵn tag trên <mark>monitor.Stats</mark>. <mark>v any</mark> là tham số "kiểu gì cũng được", giống <mark>json.Unmarshal</mark>.
- Tên trả về <mark>(found bool, err error)</mark>: Go cho phép **đặt tên giá trị trả về**, ở đây chỉ để chữ ký hàm tự giải thích, không dùng để <mark>return</mark> trần.

**Receiver nil.** Dòng <mark>if c == nil { return false, nil }</mark> ở đầu mỗi phương thức là điểm đáng nói nhất của file này. Trong Go, gọi phương thức trên một con trỏ nil **không panic**, miễn là bên trong phương thức không chạm vào trường của nó. Thế nên <mark>var c *cache.Cache</mark> (nil) vẫn gọi được <mark>c.Get(...)</mark>, và nhận lại "không tìm thấy". Nhờ vậy handler ở bước 3 không cần <mark>if s.cache != nil</mark> rải khắp nơi, và máy dev không cài Redis vẫn chạy được <mark>pulsed</mark>. Kỹ thuật này hợp với những phụ thuộc **tùy chọn** có hành vi mặc định rõ ràng (cache: luôn miss; limiter: luôn cho qua). Đừng lạm dụng cho phụ thuộc bắt buộc như database, ở đó nil phải là lỗi ngay lúc khởi động.

#### Bước 2: Package ratelimit
```go
// internal/ratelimit/ratelimit.go
// Package ratelimit giới hạn số request trong một khoảng thời gian.
package ratelimit

import (
	"context"
	"time"

	"github.com/redis/go-redis/v9"
)

// Limiter cho phép tối đa `limit` lần trong mỗi `window` cho mỗi key (ví dụ mỗi IP).
// Dùng Redis nên nhiều pulsed chạy song song vẫn đếm chung một số.
type Limiter struct {
	rdb    *redis.Client
	limit  int
	window time.Duration
}

func New(rdb *redis.Client, limit int, window time.Duration) *Limiter {
	if rdb == nil {
		return nil
	}
	return &Limiter{rdb: rdb, limit: limit, window: window}
}

// Allow trả về true nếu key còn trong hạn mức. Không có Redis (receiver nil) thì luôn cho qua.
// Thuật toán "cửa sổ cố định": INCR một key, lần đầu thì đặt hạn = window.
func (l *Limiter) Allow(ctx context.Context, key string) (allowed bool, retryAfter time.Duration, err error) {
	if l == nil {
		return true, 0, nil
	}
	key = "ratelimit:" + key

	n, err := l.rdb.Incr(ctx, key).Result()
	if err != nil {
		return false, 0, err
	}
	if n == 1 {
		// Lần đầu trong cửa sổ: đặt hạn. Các lần sau giữ nguyên hạn cũ.
		if err := l.rdb.Expire(ctx, key, l.window).Err(); err != nil {
			return false, 0, err
		}
	}
	if n > int64(l.limit) {
		ttl, _ := l.rdb.TTL(ctx, key).Result()
		return false, ttl, nil
	}
	return true, 0, nil
}
```
Thuật toán **cửa sổ cố định** (fixed window): key <mark>ratelimit:1.2.3.4</mark> là một số đếm. Request đầu tiên tạo key (<mark>INCR</mark> trên key chưa có cho ra 1) và đặt hạn 60 giây. Các request sau chỉ tăng số. Quá 10 thì chặn, và <mark>TTL</mark> cho biết còn bao lâu nữa key tự xóa, tức là bao lâu nữa được thử lại.

Vì sao <mark>INCR</mark> mà không phải "GET rồi SET +1"? Hai request tới cùng lúc đều GET được 9, đều SET 10, bộ đếm hụt một. <mark>INCR</mark> làm cả hai việc trong một lệnh, Redis xử lý từng lệnh tuần tự, nên không bao giờ hụt. Đây là cùng bài toán race condition của bài 081, chỉ khác chỗ giải quyết.

Vì sao đếm trong Redis thay vì một <mark>map</mark> có mutex trong <mark>pulsed</mark>? Vì bài 163 sẽ chạy nhiều bản <mark>pulsed</mark> sau load balancer. Đếm trong bộ nhớ thì mỗi bản đếm riêng, kẻ dò mật khẩu được 10 lần nhân số bản. Redis là bộ đếm chung. Nếu bạn chắc chắn chỉ chạy một bản, thư viện chuẩn mở rộng <mark>golang.org/x/time/rate</mark> cho thuật toán token bucket trong bộ nhớ, không cần Redis.

Điểm yếu của cửa sổ cố định: 10 request ở giây thứ 59 và 10 request nữa ở giây thứ 61 đều được, tức là 20 request trong 2 giây. Với đăng nhập, điều đó chấp nhận được. Khi cần chặt hơn (API công khai, chống scraping như bài 092) thì dùng **sliding window** hoặc **token bucket**, phức tạp hơn vài dòng Lua, để dành bài tập.

<mark>New</mark> nhận <mark>nil</mark> và trả về <mark>nil</mark>: không có Redis thì không có limiter, và <mark>Allow</mark> trên limiter nil luôn cho qua. Cùng ý tưởng với bước 1.

#### Bước 3: Middleware rate limit
```go
// internal/api/ratelimit.go
package api

import (
	"log/slog"
	"net"
	"net/http"
	"strconv"
)

// rateLimit chặn client gọi quá nhiều, tính theo IP. Dùng cho đăng nhập, đăng ký.
func (s *Server) rateLimit(next http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		allowed, retryAfter, err := s.limiter.Allow(r.Context(), clientIP(r))
		if err != nil {
			// Redis lỗi thì cho qua, có log; đừng để toàn bộ đăng nhập chết theo Redis.
			slog.Error("rate limit lỗi", "error", err)
			allowed = true
		}
		if !allowed {
			w.Header().Set("Retry-After", strconv.Itoa(int(retryAfter.Seconds())+1))
			writeError(w, http.StatusTooManyRequests, "bạn thao tác quá nhanh, thử lại sau ít phút")
			return
		}
		next(w, r)
	}
}

// clientIP lấy IP của client. Khi đứng sau reverse proxy (nginx, Cloudflare)
// IP thật nằm trong X-Forwarded-For; chỉ tin header này khi bạn chắc có proxy.
func clientIP(r *http.Request) string {
	host, _, err := net.SplitHostPort(r.RemoteAddr)
	if err != nil {
		return r.RemoteAddr
	}
	return host
}
```
- Middleware này nhận và trả về <mark>http.HandlerFunc</mark> (không phải <mark>http.Handler</mark> như <mark>logging</mark> ở bài 154) để gắn gọn vào từng route: <mark>s.rateLimit(s.login)</mark>.
- **429 Too Many Requests** kèm header <mark>Retry-After</mark> (giây) là cách chuẩn để nói "đợi chút rồi thử lại", client tử tế sẽ đọc header này. Cộng 1 để làm tròn lên.
- <mark>r.RemoteAddr</mark> có dạng <mark>ip:port</mark>, <mark>net.SplitHostPort</mark> tách ra, và nó hiểu cả IPv6 dạng <mark>[::1]:54321</mark>. Khi bạn deploy sau nginx hay Cloudflare, mọi request có <mark>RemoteAddr</mark> là IP của proxy, phải đọc header <mark>X-Forwarded-For</mark>. Nhưng header đó ai cũng gửi giả được, nên chỉ tin khi chắc chắn mọi request đều qua proxy của mình (bài 093 nói về chuyện tin header).
- **Fail-open**: Redis lỗi thì cho qua. Lựa chọn ngược lại là fail-closed, Redis chết thì không ai đăng nhập được. Với rate limit, cái giá của fail-open (vài phút không chặn được dò mật khẩu) rẻ hơn cái giá của fail-closed (toàn bộ người dùng bị khóa ngoài). Với kiểm tra quyền thì ngược lại, phải fail-closed. Hãy nghĩ câu hỏi này mỗi khi viết <mark>if err != nil</mark> trong middleware.

Vì sao chỉ giới hạn đăng nhập và đăng ký? Hai endpoint này là cửa cho dò mật khẩu (bài 088) và tạo tài khoản rác (bài 086), và không cần token nên ai cũng gọi được. Các route còn lại đã có token, muốn giới hạn thì tính theo user id thay vì IP. Rack::Attack ở bài 087 làm đúng việc này trong Rails.

#### Bước 4: Server nhận phụ thuộc qua struct
Hàm <mark>api.New</mark> đã có 4 tham số, thêm cache và limiter là 6. Gọi <mark>api.New(a, b, c, d, nil, nil)</mark> không ai đọc nổi tham số nào là gì. Go không có tham số mặc định hay tham số có tên, cách thay thế là **một struct**:
```go
// internal/api/server.go
// Package api là HTTP API của pulsed.
package api

import (
	"net/http"

	"github.com/thachnguyenp/pulse/internal/auth"
	"github.com/thachnguyenp/pulse/internal/cache"
	"github.com/thachnguyenp/pulse/internal/checker"
	"github.com/thachnguyenp/pulse/internal/monitor"
	"github.com/thachnguyenp/pulse/internal/ratelimit"
	"github.com/thachnguyenp/pulse/internal/user"
)

// Deps là mọi thứ handler cần. Cache và Limiter có thể nil (không dùng Redis).
type Deps struct {
	Monitors monitor.Store
	Users    user.Store
	Checker  *checker.Checker
	Tokens   *auth.Tokens
	Cache    *cache.Cache
	Limiter  *ratelimit.Limiter
}

// Server giữ các phụ thuộc, mỗi handler là một phương thức của nó.
type Server struct {
	monitors monitor.Store
	users    user.Store
	checker  *checker.Checker
	tokens   *auth.Tokens
	cache    *cache.Cache
	limiter  *ratelimit.Limiter
}

// New tạo Server với các phụ thuộc được truyền vào.
func New(d Deps) *Server {
	return &Server{
		monitors: d.Monitors, users: d.Users, checker: d.Checker,
		tokens: d.Tokens, cache: d.Cache, limiter: d.Limiter,
	}
}

// Handler trả về http.Handler với toàn bộ route và middleware.
func (s *Server) Handler() http.Handler {
	mux := http.NewServeMux()

	mux.HandleFunc("GET /healthz", s.healthz)
	mux.HandleFunc("POST /auth/register", s.rateLimit(s.register))
	mux.HandleFunc("POST /auth/login", s.rateLimit(s.login))

	// Các route dưới đây bắt buộc đăng nhập.
	protected := func(pattern string, h http.HandlerFunc) {
		mux.Handle(pattern, s.requireAuth(h))
	}
	protected("GET /me", s.me)
	protected("GET /monitors", s.listMonitors)
	protected("POST /monitors", s.createMonitor)
	protected("GET /monitors/{id}", s.getMonitor)
	protected("DELETE /monitors/{id}", s.deleteMonitor)
	protected("POST /monitors/{id}/check", s.checkMonitor)
	protected("GET /monitors/{id}/checks", s.listChecks)
	protected("GET /monitors/{id}/stats", s.monitorStats)
	protected("GET /monitors/{id}/incidents", s.listIncidents)

	return recoverPanic(logging(mux))
}

func (s *Server) healthz(w http.ResponseWriter, r *http.Request) {
	writeJSON(w, http.StatusOK, map[string]string{"status": "ok"})
}
```
Trường của <mark>Deps</mark> viết hoa (export) để <mark>main</mark> gán được, trường của <mark>Server</mark> viết thường vì chỉ handler dùng. Trường nào không gán sẽ là zero value, tức <mark>nil</mark>, và nhờ bước 1, 2 thì <mark>nil</mark> có nghĩa "không dùng". Đây là cách Go thay cho tham số tùy chọn, bạn sẽ gặp ở nhiều thư viện (<mark>http.Server{Addr: ..., Handler: ...}</mark> chính là ví dụ).

#### Bước 5: Cache-aside cho stats
Trong <mark>internal/api/monitors.go</mark>, thêm hai import <mark>fmt</mark>, <mark>log/slog</mark>, và sửa hai handler:
```go
// internal/api/monitors.go (sửa monitorStats và thêm statsKey)
func statsKey(monitorID int64) string {
	return fmt.Sprintf("stats:%d", monitorID)
}

// monitorStats trả về uptime và độ trễ trung bình 24 giờ qua.
// Kiểu "cache-aside": có trong cache thì trả luôn, không thì tính rồi cất vào cache.
func (s *Server) monitorStats(w http.ResponseWriter, r *http.Request) {
	m, ok := s.findMonitor(w, r)
	if !ok {
		return
	}

	var stats monitor.Stats
	found, err := s.cache.Get(r.Context(), statsKey(m.ID), &stats)
	if err != nil {
		slog.Error("đọc cache lỗi", "error", err) // cache hỏng thì coi như miss
	}
	if found {
		w.Header().Set("X-Cache", "HIT")
		writeJSON(w, http.StatusOK, stats)
		return
	}

	stats, err = s.monitors.Stats(r.Context(), m.ID, time.Now().Add(-24*time.Hour))
	if err != nil {
		writeError(w, http.StatusInternalServerError, "lỗi đọc dữ liệu")
		return
	}
	s.cache.Set(r.Context(), statsKey(m.ID), stats, 30*time.Second)
	w.Header().Set("X-Cache", "MISS")
	writeJSON(w, http.StatusOK, stats)
}
```
Và trong <mark>checkMonitor</mark>, ngay sau khi lưu kết quả thành công:
```go
// internal/api/monitors.go (thêm vào checkMonitor, sau SaveCheck)
```

Cache-aside có hai vấn đề kinh điển, và code trên trả lời cả hai:
1. **Dữ liệu cũ** (stale). Scheduler cứ 10 đến 60 giây lại có kết quả mới, cache 30 giây nghĩa là con số có thể trễ tối đa 30 giây. Chấp nhận được với một con số thống kê. Riêng kiểm tra thủ công (<mark>POST .../check</mark>) thì người dùng đang nhìn màn hình chờ, nên **xóa cache ngay** (invalidation) để lần gọi stats kế tiếp thấy kết quả mới. Quy tắc: TTL cho trường hợp thường, invalidation cho chỗ người dùng kỳ vọng thấy ngay. Bài 141 bạn đã gặp đúng cặp này ở Next.js (<mark>revalidate</mark> và <mark>revalidatePath</mark>).
2. **Stampede**: cache vừa hết hạn, 1000 request tới cùng lúc, cả 1000 đều miss và cùng đập vào PostgreSQL. Với Pulse chưa phải lo, nhưng khi có thì <mark>golang.org/x/sync/singleflight</mark> gom các request cùng key lại, chỉ một request tính, số còn lại chờ dùng chung kết quả. Để ở bài tập.

Header <mark>X-Cache</mark> không bắt buộc, nhưng rất tiện khi debug bằng <mark>curl -i</mark>: thấy ngay request đó đi đường nào.

#### Bước 6: Nối vào main và config
Thêm <mark>RedisURL string</mark> vào <mark>Config</mark>, đọc từ <mark>REDIS_URL</mark>, **không bắt buộc**. Trong <mark>cmd/pulsed/main.go</mark>, sau khi database sẵn sàng:
```go
// cmd/pulsed/main.go (thêm sau slog.Info("database sẵn sàng"))
	// Redis là tùy chọn: không có thì cache và rate limit tự tắt.
	var rc *cache.Cache
	if cfg.RedisURL != "" {
		if rc, err = cache.Connect(ctx, cfg.RedisURL); err != nil {
			return err
		}
		defer rc.Close()
		slog.Info("redis sẵn sàng")
	}
```
và thay lời gọi <mark>api.New</mark>:
```go
// cmd/pulsed/main.go (sửa)
	server := api.New(api.Deps{
		Monitors: monitors,
		Users:    store.NewUsers(db),
		Checker:  chk,
		Tokens:   tokens,
		Cache:    rc,
		Limiter:  ratelimit.New(rc.Client(), 10, time.Minute),
	})
```
Chuỗi nil chạy xuyên suốt: không có <mark>REDIS_URL</mark> thì <mark>rc</mark> nil, <mark>rc.Client()</mark> trả nil (nhờ receiver nil), <mark>ratelimit.New(nil, ...)</mark> trả nil, <mark>Allow</mark> trên nil cho qua. Có <mark>REDIS_URL</mark> mà kết nối không được thì **dừng ngay** với lỗi rõ ràng: cấu hình sai là lỗi, thiếu cấu hình là lựa chọn. Thêm vào <mark>.env</mark>:
```
REDIS_URL=redis://localhost:6379/0
```

#### Thấy tận mắt
Chạy <mark>go run ./cmd/pulsed</mark>, đăng nhập lấy token rồi gọi stats hai lần:
```sh
curl -s -i -H "Authorization: Bearer $TOKEN" localhost:3000/monitors/6/stats | grep -i "x-cache\|total"
# X-Cache: MISS
# {"total_checks":5,"uptime_percent":60,"avg_latency_ms":0.8,...}
curl -s -i -H "Authorization: Bearer $TOKEN" localhost:3000/monitors/6/stats | grep -i "x-cache"
# X-Cache: HIT
curl -s -H "Authorization: Bearer $TOKEN" -X POST localhost:3000/monitors/6/check > /dev/null
curl -s -i -H "Authorization: Bearer $TOKEN" localhost:3000/monitors/6/stats | grep -i "x-cache"
# X-Cache: MISS
```
MISS, HIT, rồi lại MISS sau khi kiểm tra thủ công vì cache đã bị xóa. Giờ thử dò mật khẩu 12 lần:
```sh
for i in {1..12}; do
  curl -s -o /dev/null -w "%{http_code} " -X POST localhost:3000/auth/login -d '{"email":"an@example.com","password":"sai"}'
done
# 401 401 401 401 401 401 401 401 401 429 429 429
curl -s -i -X POST localhost:3000/auth/login -d '{"email":"an@example.com","password":"sai"}' | grep -i "retry-after\|error"
# Retry-After: 61
# {"error":"bạn thao tác quá nhanh, thử lại sau ít phút"}
```
Chín lần 401 chứ không phải mười, vì lệnh đăng nhập lấy token ở trên đã tốn một lượt. Nhìn vào Redis:
```sh
redis-cli keys '*'
# ratelimit:::1
# stats:6
```
Key <mark>ratelimit:::1</mark> trông lạ vì IP của localhost trên macOS là IPv6 <mark>::1</mark>, nối với tiền tố <mark>ratelimit:</mark>. Trên server thật bạn sẽ thấy <mark>ratelimit:14.161.x.x</mark>.

Cuối cùng, tắt Redis đi (<mark>REDIS_URL=</mark> để trống rồi chạy lại): server vẫn lên, log không có dòng "redis sẵn sàng", stats luôn <mark>X-Cache: MISS</mark>, đăng nhập không bao giờ 429. Đó là mục tiêu của bài: tính năng phụ không được kéo đổ tính năng chính.

#### Mẹo và lỗi hay gặp
- **Quên TTL** khi <mark>Set</mark>: key sống mãi, Redis đầy dần. Mọi key cache phải có hạn, kể cả khi bạn có invalidation.
- **Cache cả lỗi**: nếu <mark>Stats</mark> trả lỗi mà bạn vẫn <mark>Set</mark>, 30 giây sau mọi người nhận lỗi đó. Code trên chỉ <mark>Set</mark> sau khi thành công.
- **Cache dữ liệu riêng tư với key không có user id** là lỗi bảo mật hay gặp: người A thấy số của người B. Ở đây <mark>findMonitor</mark> đã kiểm tra quyền trước khi chạm cache, và stats của một monitor không phụ thuộc người xem, nên key chỉ cần monitor id.
- <mark>redis-cli monitor</mark> in mọi lệnh Redis đang nhận theo thời gian thực, dùng để xem code của bạn thật sự gửi gì.
- Thấy <mark>429</mark> khi đang dev vì tự gọi quá nhiều: <mark>redis-cli del ratelimit:::1</mark> hoặc <mark>redis-cli flushall</mark>.
