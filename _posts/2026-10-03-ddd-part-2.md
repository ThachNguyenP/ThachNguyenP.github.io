Hỏi 4 team trong công ty "**Product** là gì?", sẽ có 4 câu trả lời khác nhau:
- Team **Catalog** (nội dung): tên, mô tả, hình ảnh, danh mục, SEO.
- Team **Inventory** (kho): SKU, số lượng tồn, vị trí trong kho.
- Team **Shipping** (giao hàng): cân nặng, kích thước, có dễ vỡ không.
- Team **Billing** (kế toán): giá, thuế VAT.

Và đây là thứ thường xảy ra trong code
```ruby
# app/models/product.rb

class Product < ApplicationRecord
  # 60 cột, 15 association, 30 callback
  has_many :images
  has_many :stock_movements
  belongs_to :warehouse_location
  has_one :tax_rule
  validates :weight_gram, presence: true, if: :physical?
  after_save :reindex_search, :sync_stock_to_marketplace, :recalculate_shipping_fee
  # ...
end
```
Một **god object**: team nào cũng sửa, sửa chỗ này vỡ chỗ kia, migration đụng nhau liên tục.

#### Bounded context
DDD chấp nhận một sự thật: **không thể có một model duy nhất đúng cho cả công ty**. Thay vào đó, chia hệ thống thành nhiều **bounded context**. Mỗi context có model riêng, ngôn ngữ riêng, và từ "Product" chỉ có một nghĩa duy nhất **bên trong** context đó.

Thường thì mỗi subdomain (bài 094) tương ứng với một bounded context, và mỗi context do một team sở hữu.

Không cần microservice để có bounded context. Một **modular monolith** trong Rails là đủ
```
app/
  domains/
    catalog.rb
    catalog/
      product.rb
    inventory.rb
    inventory/
      stock_item.rb
    ordering.rb
    ordering/
      order.rb
      order_line.rb
    shipping/
      shipment.rb
      ghn_adapter.rb
```
Zeitwerk tự hiểu <mark>app/domains/catalog/product.rb</mark> là <mark>Catalog::Product</mark>, không cần cấu hình gì thêm.

Mỗi context có bảng riêng, chỉ chứa thứ nó quan tâm
```ruby
# app/domains/catalog.rb

module Catalog
  def self.table_name_prefix = "catalog_"
end

# app/domains/catalog/product.rb

module Catalog
  class Product < ApplicationRecord # bảng catalog_products
    has_many_attached :images
    validates :sku, :name, presence: true
  end
end
```
```ruby
# app/domains/inventory/stock_item.rb

module Inventory
  class StockItem < ApplicationRecord # bảng inventory_stock_items
    validates :sku, presence: true, uniqueness: true
    validates :quantity, numericality: { greater_than_or_equal_to: 0 }
  end
end
```
Migration cho 2 bảng, mỗi bảng chỉ có những cột mà context đó cần
```ruby
# db/migrate/xxx_create_catalog_and_inventory.rb

class CreateCatalogAndInventory < ActiveRecord::Migration[8.0]
  def change
    create_table :catalog_products do |t|
      t.string :sku, null: false, index: { unique: true }
      t.string :name, null: false
      t.timestamps
    end

    create_table :inventory_stock_items do |t|
      t.string :sku, null: false, index: { unique: true }
      t.integer :quantity, null: false, default: 0
      t.timestamps
    end
  end
end
```
Hai model cùng nói về một sản phẩm, liên kết với nhau qua <mark>sku</mark>, nhưng hoàn toàn độc lập. Team Catalog thêm cột SEO không ảnh hưởng gì tới team Inventory.

#### Giao tiếp giữa các context
Quy tắc quan trọng nhất: **không được thò tay vào model của context khác**. Ordering không được gọi <mark>Inventory::StockItem.where(...).update_all(...)</mark>. Mỗi context public ra một vài method, giống như một API nội bộ
```ruby
# app/domains/inventory.rb

module Inventory
  def self.table_name_prefix = "inventory_"

  class OutOfStock < StandardError; end

  # API public duy nhất cho các context khác
  def self.reserve(sku:, quantity:)
    updated = StockItem.where(sku:)
                       .where("quantity >= ?", quantity)
                       .update_all(["quantity = quantity - ?", quantity])
    raise OutOfStock, sku if updated.zero?
  end

  def self.release(sku:, quantity:)
    StockItem.where(sku:).update_all(["quantity = quantity + ?", quantity])
  end

  def self.available?(sku:, quantity: 1)
    StockItem.exists?(["sku = ? AND quantity >= ?", sku, quantity])
  end
end
```
Ordering chỉ biết <mark>Inventory.reserve</mark>, không biết bảng, không biết cột. Sau này Inventory đổi sang Redis (bài 084), hay tách ra thành service riêng, Ordering không phải sửa gì.

Để đảm bảo không ai vi phạm, có thể dùng gem <mark>packwerk</mark> của Shopify: mỗi context khai báo nó được phép phụ thuộc vào context nào, và CI sẽ báo lỗi nếu có code gọi sai.
```yaml
# app/domains/ordering/package.yml

enforce_dependencies: true
dependencies:
  - app/domains/inventory
  - app/domains/catalog
```

#### Context map
Khi đã có nhiều context, cần một bản đồ cho biết chúng **quan hệ với nhau thế nào**, gọi là **context map**. Vài kiểu quan hệ hay gặp:

| Kiểu | Ý nghĩa | Ví dụ |
|---|---|---|
| **Customer / Supplier** | Context upstream cung cấp, downstream sử dụng, 2 bên thương lượng API | Inventory (supplier) cung cấp <mark>reserve</mark> cho Ordering (customer) |
| **Shared kernel** | 2 context dùng chung một phần code nhỏ | Value object <mark>Money</mark> (bài 096) |
| **Conformist** | Downstream chấp nhận dùng nguyên model của upstream, không có quyền đòi hỏi | Dùng nguyên format dữ liệu của sàn TMĐT |
| **Anticorruption layer** | Downstream dựng một lớp dịch để model bên ngoài không làm "bẩn" model của mình | Tích hợp API của đơn vị vận chuyển |
| **Open host service** | Upstream public một API chuẩn cho nhiều bên dùng | REST/gRPC API cho mobile app, đối tác |

Vẽ map này ra (chỉ cần box và mũi tên trên bảng trắng) giúp cả team thấy ngay ai phụ thuộc ai, thay đổi chỗ nào sẽ ảnh hưởng tới ai.

#### Anticorruption layer
Đây là pattern tôi dùng nhiều nhất. Ví dụ tích hợp GHN (Giao Hàng Nhanh): API trả về <mark>status: "ready_to_pick"</mark>, <mark>"delivering"</mark>, <mark>"delivered"</mark>, <mark>"return"</mark>... với tên field kiểu của họ. Nếu dùng thẳng các giá trị đó trong code, khi chuyển sang GHTK hay Viettel Post, phải sửa khắp nơi.

Thay vào đó, viết một adapter dịch về ngôn ngữ của Shipping context
```ruby
# app/domains/shipping/ghn_adapter.rb

module Shipping
  class GhnAdapter
    STATUS_MAP = {
      "ready_to_pick" => :awaiting_pickup,
      "picking"       => :awaiting_pickup,
      "delivering"    => :in_transit,
      "delivered"     => :delivered,
      "return"        => :returning,
      "returned"      => :returned
    }.freeze

    def initialize(client: Ghn::Client.new)
      @client = client
    end

    def tracking(shipment)
      data = @client.order_detail(order_code: shipment.carrier_code)

      TrackingInfo.new(
        status: STATUS_MAP.fetch(data["status"], :unknown),
        expected_at: Time.zone.parse(data["leadtime"])
      )
    end
  end
end
```
Toàn bộ "ngôn ngữ GHN" chỉ nằm trong file này. Phần còn lại của Shipping chỉ biết <mark>:in_transit</mark>, <mark>:delivered</mark>. Thêm đơn vị vận chuyển mới chỉ là viết thêm một adapter.

#### Tóm tắt
- Một từ có thể mang nhiều nghĩa ở các team khác nhau, đừng cố nhồi tất cả vào một model.
- Chia hệ thống thành các **bounded context**, mỗi context có model và bảng riêng. Modular monolith là đủ, không cần microservice.
- Các context gọi nhau qua **API public**, không chọc vào model của nhau.
- Dùng **anticorruption layer** khi tích hợp với hệ thống bên ngoài.

Đã có ranh giới rồi, bài tiếp theo sẽ đi vào bên trong một context, bắt đầu với 2 viên gạch cơ bản nhất: **Entity** và **Value object**.
