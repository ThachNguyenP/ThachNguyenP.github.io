Bài trước đã đặt mọi quy tắc của đơn hàng vào aggregate <mark>Order</mark>. Nhưng có những logic không thuộc về riêng aggregate nào, và có những việc phải xảy ra **sau khi** đặt hàng ở những context khác: trừ kho, gửi email, tạo phiếu giao hàng. Bài này giới thiệu 2 công cụ cho 2 vấn đề đó.

#### Domain service
Tính tiền giảm giá khi áp mã khuyến mãi phụ thuộc vào:
- **Đơn hàng**: tổng tiền, các sản phẩm trong đơn.
- **Mã giảm giá**: giảm theo % hay số tiền cố định, giảm tối đa bao nhiêu, đơn tối thiểu bao nhiêu.
- **Khách hàng**: hạng thành viên, đây là lần mua đầu tiên hay không.

Đặt vào <mark>Order</mark> thì Order phải biết quá nhiều về khuyến mãi. Đặt vào <mark>Coupon</mark> thì Coupon phải biết cấu trúc đơn hàng. Lúc này dùng **domain service**: một object **không có trạng thái**, chứa logic nghiệp vụ liên quan tới nhiều aggregate, và được đặt tên theo ubiquitous language.
```ruby
# app/domains/promotion/discount_calculator.rb

module Promotion
  class DiscountCalculator
    class NotEligible < StandardError; end

    def self.call(coupon:, subtotal:, first_order:)
      raise NotEligible, "Mã đã hết hạn" if coupon.expired?
      raise NotEligible, "Chỉ áp dụng cho đơn đầu tiên" if coupon.first_order_only? && !first_order
      raise NotEligible, "Đơn tối thiểu #{coupon.min_subtotal}" if subtotal < coupon.min_subtotal

      discount =
        if coupon.percentage?
          subtotal.with(amount: subtotal.amount * coupon.percent / 100)
        else
          coupon.fixed_amount
        end

      [discount, coupon.max_discount, subtotal].compact.min
    end
  end
end
```
Để ý nó nhận và trả về **value object** <mark>Money</mark> (bài 096), không đụng tới database, nên test cực kỳ dễ.

Lưu ý: hãy dùng domain service **có chừng mực**. Nếu logic chỉ liên quan đến một entity, đặt nó vào entity. Lạm dụng domain service sẽ dẫn lại về anemic domain model.

#### Domain service khác Application service
Các "service object" trong Rails mà chúng ta hay viết (<mark>app/services/xxx_service.rb</mark>) thường là **application service**, một khái niệm khác:

| | Domain service | Application service |
|---|---|---|
| Chứa | Quy tắc nghiệp vụ | Điều phối một use case |
| Biết về DB, job, email? | Không | Có |
| Ví dụ | <mark>DiscountCalculator</mark> | <mark>PlaceOrder</mark>: load order, gọi <mark>order.place!</mark>, lưu lại |
| Domain expert đọc hiểu? | Có | Chỉ là các bước |

Application service nên **mỏng**: load aggregate, gọi method của domain, lưu lại. Nếu thấy <mark>if/else</mark> nghiệp vụ trong application service, nhiều khả năng nó nên được chuyển vào domain. Bài 099 sẽ có ví dụ đầy đủ.

#### Domain event
Domain expert hay nói: *"**Khi** khách đặt hàng **thì** giữ hàng trong kho, gửi email xác nhận, và cộng điểm thành viên"*. Chữ "khi" chính là dấu hiệu của một **domain event**: một sự kiện **đã xảy ra** trong domain mà các phần khác quan tâm.

Cách viết thường thấy trong Rails
```ruby
class Order < ApplicationRecord
  after_create :reserve_stock, :send_confirmation_email, :add_loyalty_points, :notify_slack
end
```
Order phải biết tới kho, email, điểm thưởng, Slack... Thêm một tính năng là phải sửa Order. Domain event đảo ngược sự phụ thuộc: Order chỉ thông báo **"tôi đã được đặt"**, ai quan tâm thì tự đăng ký lắng nghe.

Event đặt tên ở **thì quá khứ**, là value object bất biến
```ruby
# app/domains/ordering/order_placed.rb

module Ordering
  OrderPlaced = Data.define(:order_id, :customer_id, :lines, :total_amount, :occurred_at)
end
```

#### Aggregate ghi nhận event
Aggregate không tự gửi event, nó chỉ **ghi lại**. Event chỉ được gửi đi **sau khi transaction commit thành công**, nếu không sẽ có trường hợp email đã gửi mà đơn hàng bị rollback.
```ruby
# app/domains/shared/records_events.rb

module Shared
  module RecordsEvents
    extend ActiveSupport::Concern

    included do
      after_commit :publish_domain_events
      after_rollback { domain_events.clear }
    end

    def domain_events = (@domain_events ||= [])

    private

    def record_event(event) = domain_events << event

    def publish_domain_events
      events = domain_events.dup
      domain_events.clear
      events.each { |event| Shared::EventBus.publish(event) }
    end
  end
end
```
```ruby
# app/domains/ordering/order.rb

module Ordering
  class Order < ApplicationRecord
    include Shared::RecordsEvents

    def place!
      ensure_editable!
      raise InvalidOperation, "Đơn hàng trống" if active_lines.empty?

      transaction do
        self.status = :placed
        self.placed_at = Time.current
        save!

        record_event OrderPlaced.new(
          order_id: id,
          customer_id:,
          lines: active_lines.map { |l| { sku: l.sku, quantity: l.quantity } },
          total_amount: total.amount,
          occurred_at: placed_at
        )
      end
    end
  end
end
```
Tại sao lại bọc <mark>save!</mark> và <mark>record_event</mark> trong <mark>transaction</mark>? Vì cần <mark>id</mark> của order (có sau khi save) để tạo event, nhưng nếu <mark>save!</mark> đứng một mình thì nó commit ngay và <mark>after_commit</mark> chạy **trước** khi event kịp được ghi nhận. Có <mark>transaction</mark> bao ngoài, <mark>after_commit</mark> chỉ chạy khi block kết thúc. Nếu <mark>place!</mark> được gọi bên trong một transaction lớn hơn, block này tự gộp vào transaction đó, event sẽ được gửi khi transaction ngoài cùng commit.

#### Event bus
Một event bus đơn giản là đủ cho modular monolith
```ruby
# app/domains/shared/event_bus.rb

module Shared
  module EventBus
    @subscribers = Hash.new { |h, k| h[k] = [] }

    def self.subscribe(event_class, &handler)
      @subscribers[event_class] << handler
    end

    def self.publish(event)
      @subscribers[event.class].each { |handler| handler.call(event) }
    end
  end
end
```
Các context tự đăng ký event mà nó quan tâm. Đặt trong <mark>to_prepare</mark> để chạy lại sau mỗi lần code reload ở development
```ruby
# config/initializers/domain_events.rb

Rails.application.config.to_prepare do
  Shared::EventBus.subscribe(Ordering::OrderPlaced) do |event|
    Inventory::ReserveForOrderJob.perform_later(event.order_id, event.lines)
  end

  Shared::EventBus.subscribe(Ordering::OrderPlaced) do |event|
    OrderMailer.confirmation(event.order_id).deliver_later
  end

  Shared::EventBus.subscribe(Ordering::OrderPlaced) do |event|
    Loyalty::AddPointsJob.perform_later(event.customer_id, event.total_amount)
  end
end
```
Handler chỉ **đẩy job**, không xử lý trực tiếp. Lý do: gửi email lỗi thì không nên làm lỗi cả request đặt hàng, và job có retry.

#### Eventual consistency
Inventory xử lý event như sau
```ruby
# app/domains/inventory/reserve_for_order_job.rb

module Inventory
  class ReserveForOrderJob < ApplicationJob
    def perform(order_id, lines)
      ActiveRecord::Base.transaction do
        lines.each { |line| Inventory.reserve(sku: line[:sku], quantity: line[:quantity]) }
      end
      Shared::EventBus.publish(StockReserved.new(order_id:))
    rescue Inventory::OutOfStock => e
      Shared::EventBus.publish(StockReservationFailed.new(order_id:, sku: e.message))
    end
  end
end
```
Và Ordering lắng nghe lại kết quả
```ruby
Shared::EventBus.subscribe(Inventory::StockReservationFailed) do |event|
  Ordering::CancelOrderJob.perform_later(event.order_id, "Hết hàng: #{event.sku}")
end
```
Đây là cái giá của việc tách aggregate: đơn hàng và tồn kho **không nhất quán ngay lập tức**, mà sẽ nhất quán **sau vài giây** (eventual consistency). Trong khoảng thời gian đó đơn hàng ở trạng thái <mark>placed</mark> nhưng chưa chắc còn hàng. Cần hỏi domain expert: điều này có chấp nhận được không? Với hầu hết các shop, câu trả lời là có, miễn là báo cho khách khi hết hàng. Nếu không chấp nhận được, có thể giữ hàng **trước** khi đặt như bài 083.

Chuỗi các bước nối nhau bằng event, có bước "hoàn tác" khi thất bại như trên, được gọi là **saga**.

#### Không làm mất event
Vẫn còn một lỗ hổng: transaction đã commit, nhưng server crash đúng lúc trước khi <mark>after_commit</mark> đẩy job. Đơn hàng đã đặt mà kho không bao giờ được trừ.

Giải pháp là **transactional outbox**: ghi event vào một bảng **trong cùng transaction** với aggregate, rồi một job riêng đọc bảng đó và gửi đi.
```ruby
# app/models/outbox_event.rb

class OutboxEvent < ApplicationRecord
  scope :pending, -> { where(published_at: nil).order(:id) }
end

# app/domains/shared/records_events.rb
# ghi thẳng vào outbox, thay vì giữ trong bộ nhớ chờ after_commit
def record_event(event)
  OutboxEvent.create!(event_type: event.class.name, payload: event.to_h)
end
```
<mark>record_event</mark> luôn được gọi bên trong transaction của aggregate, nên event và đơn hàng **cùng được lưu hoặc cùng rollback**. Job relay định kỳ đọc <mark>OutboxEvent.pending</mark>, gửi đi, rồi đánh dấu <mark>published_at</mark>. Vì có thể gửi lặp lại, handler cần **idempotent** (xử lý 2 lần cũng không sao), giống cách xử lý webhook ở bài 083 và 093.

Khi event cần đi ra **ngoài** ứng dụng, cho service khác, đây cũng là cách để đẩy event lên RabbitMQ hoặc Kafka (bài 077 - 080) một cách an toàn. Lúc đó chúng thường được gọi là **integration event**, nên có schema ổn định và chỉ chứa dữ liệu cần thiết, vì thay đổi chúng sẽ ảnh hưởng tới các team khác.

#### Tóm tắt
- **Domain service**: logic nghiệp vụ không thuộc entity nào, không trạng thái. Đừng nhầm với application service.
- **Domain event**: sự kiện đã xảy ra, đặt tên thì quá khứ. Aggregate ghi nhận, gửi đi **sau commit**.
- Giữa các aggregate/context dùng event, chấp nhận **eventual consistency**.
- Cần chắc chắn không mất event thì dùng **outbox**, và handler phải **idempotent**.

Bài cuối sẽ ghép tất cả lại thành một flow hoàn chỉnh trong Rails.
